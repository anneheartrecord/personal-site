自从 Gemini 4 出来之后，大家其实会发现 Gemini 的模型又回到了第一梯队。我这几个月的整个开发工作流以及平常使用 AI 的方式，又发生了一些变化。

一定要根据不同模型的特点去区别用途：

1. Claude：目前依旧是最量大管饱的，因为我的 Gemini 开的是 Pro 套餐，没那么耐用，尤其是我用它的 Orchestrator 模式，稍微做 3 到 4 个大一点的任务，5 小时额度就会耗完。所以我的日常工作主力还是 Claude Opus。虽然这段时间传闻 Opus 被降智了一些，但整体来说还是符合预期的，依旧能保持许愿式编程、许愿式完成任务的水平。所谓许愿式编程，就是不需要人为把工作流搞得很重，也不需要额外用复杂的配置，大白话配合它本身的 goal + loop 等命令，不需要任何其他插件就能把任务完成得很好。

2. GPT：用来做 Code Review，我已经很久没有单独用过 GPT 了，但大家都知道它的模型倾向很保守、偏防御性。基于这些特性，我的 Code Review 全是用 Codex Connector 去做的，这是 Codex 给 GitHub 的一个组件。配上之后，每个 PR 都能自动用 GPT 进行 review。这样至少能保证我们上线的代码在语法层面基本没有任何问题；一旦出问题，更多是 AI 理解功能出现了偏差，而不是代码本身的问题。

3. Gemini：日常开发与文本输出，Gemini 我最近高强度用了几天，发现它基本上也到了许愿式编程的阶段。而且 Gemini 还有一个非常好的特点，就是它说人话。之前我研究过它为什么会说人话，主要是它的后训练 RL Model 和 GPT、Claude 不太一样，对语义压缩没有那么严重，输出内容的信息密度更适中，更容易被人脑接受。所以我现在的很多内部报告分析，都会让 Gemini 来做，或者 Claude 加 Gemini 来做，但文本、文案这些东西一定是 Gemini 出的，能极大减少我们的认知负担。

未来按照不同模型的特征去对任务进行区分，应该会是一个趋势。不会有一个大模型把所有场景都吃掉，因为每家模型在训练数据和后训练策略上都不一样，最终展现出的模型特征也完全不同。

Opus 5.5 和 Gemini 4 的这几个模型，我觉得可能会是模型发展史上的一个标志性转折点。因为从这些模型开始，它们才普遍具有所谓许愿式编程或许愿式完成任务的能力。

既然现在模型已经到了这个智能水平，而且智能还在不断增长（有传言说 OA 家的内部模型已经实现 RSI 了），我觉得之后在选择模型时，可能就不用考虑最优模型了，因为模型能力已经就位。我可能还是会结合模型本身的一些特点和成本，去综合选择模型。

等哪一天国产模型也能到这种程度，而且成本还巨低的时候，我也会转向更多地使用国产模型。
