## 今日判断

今天翻下来，我更关注工具团队把 agent 往工程运行时里塞。Rauch 把 Vercel 侧 agent 的部署、沙箱隔离、失败重试和按用户计量放在一层讲；Thibault 讲 Codex 的任务交接、结果审查和人工环节；Peter Steinberger 拿真实项目压边界，指出失败常发生在第几步。我的判断是竞争点已从模型能力转到运行时：sandbox、长任务调度、计费、可观测四块做扎实，才能接住真实工作流。对一线 builder，今天该做的是给 agent 一个能长跑、失败可回滚、成本可核算的执行环境，而不是再套一层 prompt。Aditya 和 Amjad 的讨论也落到具体项目验证与信任默认值。我会继续盯失败案例和账单：一个 agent 产品说不出单次任务成本结构和错误恢复策略，我就不信它能进生产。

### 1. Rauch 谈 agent 运行时：部署、隔离与计费正在合并

[查看原文](https://x.com/thsottiaux/status/2123557171321561133) · 来源：Thibault Sottiaux (@thsottiaux)

Thibault 说明 Codex 团队如何把任务交给 coding agent、如何审结果、哪些环节留人。重点在交互分工，不在发新模型。判断：这比 benchmark 数字更有决策价值，官方推荐交互模式可直接对照工具链；这是厂商视角，失败率和长尾任务仍需自测。若做 coding tool，官方默认交互形态就是差异化起点。

### 3. Rauch 从企业侧谈 agent 落地：权限与可审计决定上线

[查看原文](https://x.com/rauchg/status/2123553975945556144) · 来源：Guillermo Rauch (@rauchg)

Rauch 从企业客户阻力讲 agent 上线条件：权限边界、操作留痕、自动执行的批准人比模型效果更关键。判断：企业需求不是加个 SSO，责任划分才拦路；一次自动改动出问题，日志要还原哪一步、依据什么。做 to B agent 应先设计审计数据结构，再设计规划能力。

### 4. Aditya Agarwal 谈 coding agent 与模型选择：按任务分配，不押单一模型

[查看原文](https://x.com/adityaag/status/2123494873919783073) · 来源：Aditya Agarwal (@adityaag)

Aditya 谈真实项目里 coding agent 的用法与模型取舍：任务类型对应不同模型，成本、延迟、可靠性只能按场景分配。角度偏组织流程。判断：给团队推 AI 编码工具时有用，因为多模型并存的成本通常上线三个月后才显现；模型抽象层是必需品，不是过度设计。大厂代码库与十人团队约束不同，经验迁移要打折。

### 6. Peter Steinberger 用真实项目压测 coding agent 边界

[查看原文](https://x.com/steipete/status/2123487048250327497) · 来源：Peter Steinberger (@steipete)

Steinberger 用真实项目撞 coding agent 边界：哪些任务一次完成、哪些必须人接手、失败常在第几步。判断：这种带代码上下文和失败现场的内容比评测榜单可信，可对照自己项目。coding agent 瓶颈常在理解现有工程约定和验证改动安全，不在生成代码。做类似工具应把验证环节做进产品，比继续提升生成质量更能留住用户。

### 7. Amjad Masad 谈 agent 工作流里的信任与默认值

[查看原文](https://x.com/amasad/status/2123535544718418191) · 来源：Amjad Masad (@amasad)

Masad 讨论 agent 替用户做多少决定：自主权太多用户不敢用，太少退化成聊天框；这是 Replit 自动构建反复撞到的问题。判断：价值在把信任落到产品默认值，比如是否自动执行、执行前是否展示计划。多数产品用“用户可配置”糊过去，实际没想清默认值偏向。默认值就是产品立场。
