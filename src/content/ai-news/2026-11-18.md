## 今日判断

我今天更关注 Agent 跑在真实系统里的细节，不是谁又发了新模型。Aaron Levie 讲企业 Agent 常见失败：模型够用，权限、数据边界和审计链没跟上，最后只能读不能写。我在几个客户现场看到同样路径：先做只读 Copilot，再逐步放开写权限，ACL 和审批是主要工程量。

运行时方面，Rauchg 连发几条，讲的是同一类需求：沙箱、可恢复执行、可重试步骤，靠改提示词解决不了。Claude Code 的 Thariq 讲把重复上下文拼装固化成可复用技能，不每次靠人现场写长提示。Peter Steinberger 本地并行跑多个 Agent，看着提效，账单和失败重试才是日常。

我给一线 builder 的判断：今年剩下时间别把主要精力花在换模型上。先做三件事：给 Agent 一个能查权限的入口，给每一步一个可重放日志，把高频任务固化成模板文件。模型换代随时能跟，这三样不做，换代也救不回来。

### 1. Levie：企业 Agent 卡在权限和上下文，不在模型

[查看原文](https://x.com/levie/status/2122508098351038532) · 来源：Aaron Levie (@levie)

Box 的 CEO Aaron Levie 谈企业 Agent 落地瓶颈：模型能力不是主因，权限、数据边界和审批链才是。多数团队先让 Agent 只读，再逐条放开写权限，中间补 ACL、审计和回滚。这解释企业内部 Agent 上线慢和 demo 进不了生产。判断：做 to B Agent 应把权限层当产品做，不是接入杂活。

<a id="20261118-02"></a>

### 2. Vercel 把 Agent 当成有生命周期的运行时来设计

[查看原文](https://x.com/rauchg/status/2122415506451841215) · 来源：Guillermo Rauch (@rauchg)

Vercel 的 Guillermo Rauch 从平台侧列 Agent 运行时需求：沙箱、可恢复长任务、每一步可观测。这些点不新，但放进同一套部署模型后，Agent 不再是后端函数，而是有生命周期的执行体。做 Agent 产品时，这类基础设施决定能否做超过 30 秒的任务。判断：长任务 Agent 的竞争先发生在执行可靠性，不在提示词。

<a id="20261118-03"></a>

### 3. Claude Code 团队把重复劳动固化成可复用技能

[查看原文](https://x.com/trq212/status/2122438326431154210) · 来源：Thariq (@trq212)

Anthropic 的 Thariq 讲 Claude Code 用法：把重复的上下文拼装和操作步骤固化成可复用技能，不每次现场手写长提示。机制上省的是每次会话启动成本：规则、目录结构、验证命令预先写死，模型只负责判断。当天互动高，说明不少人在用 coding agent 做重复工作。判断：coding agent 的效率差距接下来主要来自这些沉淀文件的质量，不是模型选择。

### 4. 本地并行跑多个 coding agent 的真实成本账

[查看原文](https://x.com/steipete/status/2122463466304971068) · 来源：Peter Steinberger (@steipete)

Peter Steinberger 讲本地并行跑多个 coding agent 的做法和代价。多开 Agent 看似提效，真正卡人的是上下文隔离、失败重试和 token 账单，他给出了具体数字。这类复盘比发布新工具更有用：它直接说明何时该并行，何时并行只是烧钱。判断：本地跑 Agent 的团队应先做任务队列和成本上限，再谈并行数量。

### 5. Every 把 Agent 接进编辑流程后的取舍

[查看原文](https://x.com/danshipper/status/2122541401804054826) · 来源：Dan Shipper (@danshipper)

Every 的 Dan Shipper 记录把 Agent 接进编辑流程后的取舍：哪些环节交给 Agent 起草，哪些必须人做终审。他关注自动化后编辑注意力放在哪，而非能不能自动写。对内容团队，这比模型排行榜有用。判断：内容类 Agent 产品的差异化落在审核和版本管理，写得好坏反而最先被解决。

### 6. 产品经理用 Agent 做原型，边界在哪里

[查看原文](https://x.com/petergyang/status/2122347721298510021) · 来源：Peter Yang (@petergyang)

Peter Yang 从产品经理视角讲用 Agent 做原型的边界：适合快速铺出可点界面和流程，不适合直接接真实数据。做法是先让 Agent 产出结构，再手工替换关键依赖，避免原型假数据被当真。对做内部工具有参考价值。判断：Agent 生成原型的价值在缩短讨论时间，不在交付，交付前人工替换不能省。

### 7. 给 Agent 读的网页该长什么样

[查看原文](https://x.com/rauchg/status/2122396034186014919) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 讨论面向 Agent 的网站形态：页面是否直接吐 markdown，是否为爬取和调用准备结构化入口。互动高，因为流量的一部分不再是人浏览，而是 Agent 执行。对工具和文档站，这意味着重新设计信息暴露方式。判断：未来一年为 Agent 优化可读性会像当年做 SEO 一样成为默认工作。

### 8. Gemini 应用侧这次更新，看点在交互位置

[查看原文](https://x.com/joshwoodward/status/2122453269842886788) · 来源：Josh Woodward (@joshwoodward)

Google 的 Josh Woodward 讲 Gemini 应用侧一次能力更新，落点在普通用户直接感知的功能，不是模型榜单。大厂更新值得看它把能力放在哪一步交互，这往往预示下一批产品怎么做。判断：应用层小改动会先吃掉一部分独立产品需求，做垂直工具的人要盯交互位置，不只盯 API。
