## 今日判断

今天最大的信号是 Claude 把项目管理层搬进了模型侧。Boris 和 Thariq 都在说同一件事：一个 project 是一个常驻 agent，负责记忆、拆线程、派子 agent，你不再手动管理 session，而是把想法丢进去。这比多开几个 chat window 有用得多，因为真正的瓶颈从来不是单次生成质量，而是上下文怎么在任务之间传递、谁来记住上周那个决定。Cat Wu 说她已经每天用它做批量任务再收汇总，这个体感比任何 benchmark 都说明问题。

另一个我留意的方向是 agent 开始自己承担运营动作。Nikunj 给一个儿童零食站写了每天醒来跑一圈的 Claude agent，检查目录、砍掉下架品、找内容选题、看 Search Console、写稿。这产品本身不重要，重要的是他把 agent 放进了 SEO 这种有明确反馈信号的工作流里，能自我纠正，而不是只做一次性生成。这类 daily loop 会先在小站、独立开发者的场景里跑通，因为它容错高、信号清晰。

Aaron Levie 提到 agent 已经占推理量的大头，我信这个方向，但更值得看的不是总量，而是 token 花在哪。如果大部分是 24/7 无人值守的 background 任务，那 infra 的瓶颈会从单次延迟转向调度、失败重试和成本可观测性。Vercel 把部署压到 1 秒也是在配合这个趋势：agent 产出的东西必须能立刻上线，不然自动化的价值会被人工发布环节吃掉。我的判断是，接下来一年做工具的人该盯的不是更聪明的模型，而是让 agent 能被信任地长时间跑、跑挂了能恢复、花钱能看见。

### 1. Boris Cherny：我已经不管理 session 了，Claude Projects 会自己拆线程记上下文

[查看原文](https://x.com/bcherny/status/2100669598995816511) · 来源：Boris Cherny (@bcherny)

Boris Cherny 说他现在写代码的方式变了：不再管理 session，想到什么就发出去，由 Claude 把想法拆进不同线程，project 记住他的工作习惯。他放出了自己昨天实际发给 Claude Code CLI 的 prompt 截图，明确说这是他大量 coding 的主场。为什么重要：过去 coding agent 的痛点是上下文在任务之间断裂，人得手动喂上下文。这种 project-as-agent 的做法把记忆和线程拆分交给模型侧，人的角色从 session 操作者变成意图输入者。我的判断是这比单次生成质量提升更能改变日常体感，因为它直接减少了每轮对话前的心智负担。

### 2. Thariq：Projects 把 Claude Tag 的架构带进 Claude Code，每个项目一个 agent 管记忆

[查看原文](https://x.com/trq212/status/2100638355872706571) · 来源：Thariq (@trq212)

Thariq 补充了 Projects 的机制：每个 project 有一个 agent 负责记忆，并把任务派给子 agent，可以要求它主动执行或按 schedule 跑。他说这比堆一堆 session 感觉好很多。为什么重要：这是把 Claude Tag 的多 agent 编排思路下放到 Claude Code，等于给单个开发者一套轻量的 orchestrator。子 agent 加常驻记忆的组合，让长任务和重复任务不再依赖人反复 prompt。我的判断是这种架构会让 coding agent 从补全工具变成项目级的协作者，但也意味着失败模式从写错代码变成编排跑偏，可观测性会变成下一个刚需。

### 3. Cat Wu：我每天用 Projects 批量发任务，再让 Claude 给汇总状态

[查看原文](https://x.com/_catwu/status/2100641163120423057) · 来源：Cat Wu (@_catwu)

Cat Wu 说她在新 Projects 里让 Claude 协调所有 session，自己批量发任务然后走开，需要时让 Claude 给聚合状态。她特别提到长期记忆会随使用演化。为什么重要：这描述的是一种新的工作节奏，人负责下批任务和收状态，中间的编排交给 agent。聚合状态这个能力很关键，因为任务一多，人最缺的是全局视图而不是单条输出。我的判断是当 agent 能主动汇报进度，人的注意力分配会变，从盯每一步变成定期 review，这要求 agent 的汇报本身要可信，否则会成为新的噪音源。

### 4. Nikunj 用 Claude agent 每天自动跑儿童零食站：巡检目录、砍品、找选题、写稿

[查看原文](https://x.com/nikunj/status/2100714665571737885) · 来源：Nikunj Kothari (@nikunj)

Nikunj 说他痴迷 self driving company 一年多，试了很多产品不达标，于是自己用 Claude 在 loop 里搭了一个儿童健康零食站。站点本身有目录和对话推荐，自主部分是一个每天醒来的 Claude agent，检查新商品、清理死品、找内容选题、查 dataforSEO 和 Google Search Console、写和改稿、并尝试接洽媒体。为什么重要：这是把 agent 放进一个有客观反馈信号的运营工作流，错了下一轮能纠。我的判断是 daily loop 加清晰指标会先在独立开发者和电商小站跑通，因为容错高、信号明确；这类场景会比企业自动化更早积累出可靠的 agent 运维经验。

### 5. Aaron Levie：agent 已占推理量大头，一年内会接近全部

[查看原文](https://x.com/levie/status/2100799668573946191) · 来源：Aaron Levie (@levie)

Aaron Levie 说 agent 已经占推理量的大头，一两年内会接近全部，token 主要来自 24/7 在后台跑任务的 agent，用于读代码变更做安全、处理工作流数据、招聘和客户勘探研究、review 所有系统和日志、执行个人任务等。他说过去一周他引入了多个一个月前技术上还做不到的新工作流。为什么重要：如果推理主力是无人值守的后台 agent，infra 需求会从单次低延迟转向调度、重试、成本可观测。我的判断是这对做 agent 平台的人是利好也是压力，利好在于需求持续，压力在于可靠性和费用控制会成为采购的硬门槛。

### 6. Guillermo Rauch：Vercel 把部署压到 1 秒，为 agent 时代的海量软件做准备

[查看原文](https://x.com/rauchg/status/2100698591417499972) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 说未来一年产出的软件可能超过计算史上总和，Vercel 前十年到 10 亿次部署，最近 10 个月又加了 14 亿。其中很多是小的、个人的、一次性的软件，从 artifact、报告、定价计算器到复杂 app 和 agent。他们把部署、上传、分配域名、全球生效压到 1 秒，包含 CDN、防火墙、不可变部署、可观测和回滚。为什么重要：agent 产出的东西必须能立刻上线，否则自动化价值被人肉发布环节吃掉。我的判断是发布速度和 agent 生成速度必须匹配，不然瓶颈只是从写代码挪到了上线流程。

### 7. Garry Tan：Memorable 用 embedding 优化记忆而不是堆更多 token

[查看原文](https://x.com/garrytan/status/2100668489178456268) · 来源：Garry Tan (@garrytan)

Garry Tan 提到 Memorable 找到了用 embedding 优化记忆的方法，而不是靠更多 token 来维持记忆，他认为这是做记忆的新方式。为什么重要：agent 长期记忆目前主流做法是把历史塞进上下文或做摘要，成本和遗忘问题都明显。用 embedding 做检索式记忆，理论上能把成本从线性增长变成按需召回。我的判断是这个方向值得做 infra 的人盯，但单条信息量有限，还需要看到具体召回质量、延迟和更新机制的实测数据才能判断是否可落地。

### 8. Guillermo Rauch：agent 紧急发版可以用 vercel --turbo --prod 走最快构建机

[查看原文](https://x.com/rauchg/status/2100682030170489160) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 说当你要 agent 快速发一个 hotfix 时，它现在可以用 vercel --turbo --prod 使用最快的构建机，并提到这个想法来自用户 garberchov 的提议。为什么重要：这是平台开始针对 agent 作为发布主体的场景做专门开关，而不是只服务人类开发者的常规发布流程。我的判断是这类小改动会累积成 agent 优先的部署体验，值得做 coding agent 和 CI 的人留意，因为 agent 发版的频率和失败模式跟人不同，需要独立的超时、重试和回滚策略。
