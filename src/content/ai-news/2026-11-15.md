## 今日判断

今天时间线上没有模型发布级别的大事，值得看的是几条来自做产品的人的具体反馈。我先听了 Training Data 那期长访谈，再回头翻了几条推文，讨论重心在挪：coding agent 这块，问题已经从能不能写出来，变成写完以后谁来验证。同一个任务跑三次给出三个不一样的补丁，怎么判断哪个能合并，在真实仓库里比任何 benchmark 分数都硬。

另一条线是 agent 和已有系统的接缝。看下来，做 infra 的人反复回到同一件事：把 agent 塞进现有代码库或内部系统，最贵的不是 token，是让它能安全地读写真实数据、出错能回滚、事后能复现。这三件事做好，产品体验的差距立刻出来；做不好，demo 再漂亮也进不了生产。所以我今天更关注带失败分析的分享，而不是又一个新 agent 框架。

我的判断是：未来几个月沉淀下来的是可观测性和回放，不是编排 DSL。谁能把一次 agent 运行完整记录、回放、在失败点插入人工检查，谁的工具就留在团队工作流里。反过来，只提供更花哨编排方式的产品，两周就会被绕开。

### 2. Garry Tan 谈 coding agent 的模型选择取舍

[查看原文](https://x.com/garrytan/status/2121464508225053153) · 来源：Garry Tan (@garrytan)

Garry Tan 把 coding agent 的实际使用和模型选择放在一起谈。讨论角度不是哪个模型跑分高，而是日常改代码时模型差异体现在哪里：补丁能不能直接应用、上下文要不要反复重喂、失败后重试成本有多高。我的判断是，coding agent 的竞争已经从模型能力转到工程细节，重试和验证这一层做扎实，产品才会被留下来。

### 3. Nikunj Kothari：agent 与 infra 叠加时的约束

[查看原文](https://x.com/nikunj/status/2121320899161010360) · 来源：Nikunj Kothari (@nikunj)

Nikunj Kothari 把 agent 工作流、底层 infra 和模型能力放进同一个语境。他点出一个容易被忽略的事实：agent 的体验上限往往由 infra 决定而不是模型——并发上去以后的限流、上下文截断、工具调用超时，都会让 demo 里很顺的流程在生产里不可用。我的判断是，做 agent 产品应该把 infra 指标和产品指标放在同一张看板上，否则会一直误判为模型不够聪明。

### 4. Peter Yang：把 agent 嵌进日常动作的编排

[查看原文](https://x.com/petergyang/status/2121430386685395022) · 来源：Peter Yang (@petergyang)

Peter Yang 讲自己怎么用 agent 的实践观察。可以看到他把 agent 嵌进日常动作时的具体编排：哪一步交给模型自由发挥，哪一步用固定脚本兜住，出错靠什么信号发现。我的判断是，目前 agent 产品的差距主要不在模型，而在编排细节的积累，这类细节只能靠自己踩坑或看别人的失败记录获得。

### 5. Amjad Masad 谈 agent 失败时的体验设计

[查看原文](https://x.com/amasad/status/2121428406764204199) · 来源：Amjad Masad (@amasad)

Amjad Masad 从把 agent 直接做成产品的角度谈真实用户手里会碰到什么，更接近产品决策：什么时候让 agent 继续跑，什么时候停下来问用户，失败提示怎么写才不让人放弃。我的判断是，agent 产品的留存问题很大一部分不在能力，而在失败时的体验设计——用户能接受 agent 做不出来，接受不了不知道它卡在哪、该改什么。

### 6. Guillermo Rauch：agent 接进部署链路后的权限与回滚

[查看原文](https://x.com/rauchg/status/2121277727940776114) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 延续一贯角度：agent 的价值出现在它和部署、构建、预览这些既有链路接上之后，而不是单独作为一个聊天框。一旦 agent 能触发真实部署，权限、审计、回滚立刻变成必须解决的问题，这恰好是大多数 agent demo 绕过去的部分。我的判断是，接下来一年开发者工具的差异会体现在这些接缝上，而不是谁的模型更强。

### 7. Dan Shipper：agent 进入团队后的流程改造

[查看原文](https://x.com/danshipper/status/2121248233510818003) · 来源：Dan Shipper (@danshipper)

Dan Shipper 谈 agent 进入团队之后发生的事，重点在人和流程怎么调整而不是工具好不好用。一个 agent 能不能留下来，往往取决于团队愿不愿意改自己的工作方式，而不是它跑得多快。我的判断是，做企业内部工具应该把组织摩擦当成产品需求处理，比如把 agent 的输出做成可审阅的中间产物，而不是直接给最终结论。

### 8. Garry Tan 谈 AI infra 侧的约束变化

[查看原文](https://x.com/garrytan/status/2121463161069228382) · 来源：Garry Tan (@garrytan)

Garry Tan 落在 AI infra 侧的观察，谈支撑层现在在发生什么。infra 的变化通常滞后一两周才传导到产品体验，但能提前看到成本、延迟、可用性这些约束会怎么变。我的判断是，infra 讨论值得看不必逐条跟，重点看有没有具体数字和架构取舍；只有观点没有机制的，跳过。
