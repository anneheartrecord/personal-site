## 今日判断

今天翻下来，真正值得记一笔的不是哪家又发了模型，而是几条关于「人怎么和 agent 分工」的一手经验。Guillermo Rauch 那条讲得很直白：你会过度指导 AI，也会指导不足，前者它比你聪明你反而拖后腿，后者它跑偏、带错 bias、丢上下文。这个「过度/不足」的钟摆，我最近自己在用 coding agent 时体感极强，真正的技能不是写提示词，而是判断什么时候该放手、什么时候该收缰。他把这称作 #0 技能，我认同，而且这几乎是所有 agent 工作流的共同瓶颈。

另一头是 Aaron Levie 讲 cyber agent 的量级：未来流经安全 agent 的 token 会比今天多 1000 倍，风险面扩张到人力根本跟不上，必须靠 agent swarm 扇出、调各种安全工具、读日志、评估企业数据风险。他强调这能力是最近几个月才出现的，前提是长时运行 agent 和 computer use 终于够用、模型也在 cyber 上训得够深。我认同这个从「模型能力够了」到「工作流才成立」的因果链，安全会是最早被 agent 吃掉的深水区之一，因为它天然量大、天然需要持续盯。

还有两条我留着是因为它们在讲同一个底层：Rauch 说模型爱用 gate、evidence、culprit、provenance、contract 这类工程词汇，因为大多工程本质是调试和审计现有系统；Nikunj 转发的那条讲 context -> harness -> judgement 的演进。两条拼起来其实是我的判断——agent 产品的竞争力会从「上下文喂得好不好」转向「judgement 做得好不好」，也就是能否在证据不足时停下来、知道自己不知道。今天没有大新闻，但这条分工线在变清晰。

### 1. Levie：安全 agent 的 token 量将涨 1000 倍，靠 swarm 才追得上风险面

[查看原文](https://x.com/levie/status/2114187326406766604) · 来源：Aaron Levie (@levie)

Levie 判断不久的将来流经 cyber agent 的 token 会比今天多 1000 倍。理由是风险面扩张速度已超过人力上限：库、工具、代码与基础设施太庞杂，大公司勉强追，多数公司根本追不上。解法是让 agent swarm 扇出、调用任意安全工具、模拟各种攻击变体、读日志、评估企业数据风险。他明确说这能力只在最近几个月才出现，前提是长时运行 agent 和 computer use 够好、模型在 cyber 上训得够深。我的判断：安全是最先被 agent 吃掉的深水区，因为它天然量大且需要持续盯，这不是买不买的问题，是人力模型本身就撑不住了。

<a id="20261026-02"></a>

### 2. Rauch：过度指导和指导不足之间的钟摆，是 agent 时代的 #0 技能

[查看原文](https://x.com/rauchg/status/2114085432749347086) · 来源：Guillermo Rauch (@rauchg)

Rauch 说用 AI 一定会有两个方向的失误：有时你过度指导，其实它比你更懂、比你更聪明，你在拖后腿；有时你指导不足，它跑偏、带错误 bias、丢上下文。他把「管理好这个超能力」列为最看重的 #0 技能。这不是空谈，而是把 agent 使用拆成一个可调的双向失败区间。我的判断：一线 builder 的差异化正从写提示词转向收放判断力，尤其在做 coding tool 和 agent 产品时，产品的默认行为应该帮用户识别「现在该放手了」还是「现在该收缰了」，这本身就是产品设计问题。

<a id="20261026-03"></a>

### 3. Rauch：模型爱说 gate、provenance、contract，因为工程本质是审计

[查看原文](https://x.com/rauchg/status/2114164830403989880) · 来源：Guillermo Rauch (@rauchg)

Rauch 注意到模型特别爱用 gate、evidence、culprit、durable、provenance、contract 这类工程词汇，并指出这些词多来自「工程本质是调试和理解现有系统」——你需要扮演侦探和审计员，做取证。他顺势问：能干活的最小可行英语到底有多大？简化技术英语 ASD-STE100 约有 900 个批准词，他怀疑实际需要的远少于此。我的判断：模型的用词倾向其实是它内部工作方式的镜像，如果 agent 默认进入调试/审计模式，那模型的输出结构和 harness 设计都该围绕证据链来组织，而不是围绕自然对话。

### 4. Nikunj：从 context 到 harness 再到 judgement 的演进线

[查看原文](https://x.com/nikunj/status/2113994081345126486) · 来源：Nikunj Kothari (@nikunj)

Nikunj 用一句转发带出他自己的框架：这个领域正在从 context 演进到 harness，再到 judgement。他公开邀请做过这块产品的人一起交流产品想法。这三段其实对应了 agent 产品竞争的迁移：早期拼谁喂的上下文好，中期拼 harness 和工具编排，后期拼 judgement——也就是在信息不足时能否停下来、知道自己不知道。我的判断：多数团队还停在 harness 层，真正拉开差距的是 judgement，而 judgement 很难靠 prompt 堆出来，得靠评测和真实失败案例沉淀。

### 5. Ryo Lu：设计/编程能力来自反复摔打，AI 放大了能做的东西

[查看原文](https://x.com/ryolu_/status/2114187405251219954) · 来源：Ryo Lu (@ryolu_)

Ryo Lu 回顾自己编程和设计能力的来源：靠试错、撞墙再翻墙、读看不懂的东西、拆解、求助、重来。很多作品并不好，但足够多轮之后有东西沉淀下来，变成直觉——能在解释清楚之前就感到哪里不对。现在可以把问题丢给机器，他做出了原本可能永远做不出来的东西。我的判断：这段和今天其它几条是一条线——工具降低了执行门槛，但判断力仍然是靠失败积累的，AI 加速的是执行不是品味，builder 的护城河在后者。

### 6. JEV/TypeSafe 创始人：做决策而不是做文本的模型

[查看原文](https://www.youtube.com/@DataDrivenNYC/videos) · 来源：The MAD Podcast with Matt Turck

Matt Turck 访谈 TypeSafe 创始人 Diogo Almeida，讲 JEV——一个月前无人知晓、随后成为被大量复制的模型。Almeida 的核心主张是它在做决策而不是生成文本，并称预训练是巨大的资源浪费、认为去年本可以做出 AGI。他也回应了「这只是个分类器」的质疑，说复制者没抓住要点。我的判断：无论 JEV 最终成不成，这个方向值得盯——如果模型的价值重心从「说得像」转向「判得准」，那评测体系和产品形态都得重做，这和今天几条关于 judgement 的判断是同一件事。
