## 今日判断

我今天更关注做 agent 和 coding tool 的人在聊什么，没有把注意力放在谁又发了新模型上。Aaron Levie 那条长帖讲企业 agent 落地，讨论的是接进既有流程之后的权限分级、审计日志、失败回滚和跨系统状态同步，这些并非 demo 能不能跑的问题。这些是组织成本，不是能力上限，只有真在客户环境里部署过的人才写得出来。

Thibault 的 coding agent 更新和 Peter Yang 的横向对照指向同一件事：进步不在单次生成质量，而在一次会话里能不能持续拿到正确的仓库状态、失败之后能不能自己回到可用状态，竞争点因此移到可恢复性上。我看下来，选 coding 工具该看的是它在第几步卡住、需要人介入几次，不是榜单排名。

Thariq 讲上下文分层按需加载，Amjad 讲 agent 必须能改真实状态，两条放在一起就很清楚：接下来一年 agent 产品的差距，落在能不能安全地修改真实状态、出错时能不能收敛回来。我的判断是，把 agent 接进生产环境的团队，花在失败恢复和权限设计上的时间会超过写 prompt 的时间。给一线 builder 的动作很具体：这一版先把权限分级、失败回滚、上下文预算这三件事做完，再排新模型接入。

### 1. 企业 Agent 的难点在接入既有流程后的权限、审计与回滚

[查看原文](https://x.com/levie/status/2124252844710887549) · 来源：Aaron Levie (@levie)

Aaron Levie 复盘企业里跑 agent 的实际摩擦：能跑通演示的任务放进真实业务后，要先解决权限分级、审计日志、失败回滚和跨系统状态同步。他把 agent 当成需要治理的新成员：谁能批、能读哪些数据、出错谁兜底。判断：企业采购 agent 卡在这些流程上，不是 benchmark 高低；做 to B agent 的团队先把权限和回滚做完，再谈任务覆盖率。

<a id="20261123-02"></a>

### 2. Coding Agent 这轮更新的重点是长任务里的状态延续

[查看原文](https://x.com/thsottiaux/status/2124322968499282388) · 来源：Thibault Sottiaux (@thsottiaux)

Thibault Sottiaux 公布 coding agent 更新，重点是长任务中的上下文延续和工具调用策略，而非单次补全准确率。评论区大量开发者贴出自己仓库里的失败场景。判断：这类更新让更长的工程任务可以整体交给 agent，人的角色从写代码变成审代码。竞争点已经移到失败后能否收敛，能不能接住第二次、第三次失败才是分水岭。

<a id="20261123-03"></a>

### 3. Agent 规则按需加载，而不是堆进一个系统提示

[查看原文](https://x.com/trq212/status/2124239684536840682) · 来源：Thariq (@trq212)

Thariq 讲 agent 工作流里规则和技能的组织方式：把所有约束堆进一个系统提示，不如拆成按需加载的小块，由 agent 在具体任务里自己取用，给的是可直接落地的工程做法。这种上下文分层正在从个人技巧变成团队标准做法。对 builder 的提醒很具体：先把每次调用的上下文预算算清楚，否则提示越长、干扰项越多，行为越不稳定。

<a id="20261123-04"></a>

### 4. 同一个任务丢给几个 Coding Agent，按阶段看卡在哪

[查看原文](https://x.com/petergyang/status/2124217176655843483) · 来源：Peter Yang (@petergyang)

Peter Yang 把同一个任务丢给几个 coding agent 做对照，记录各自卡在哪一步、需要人介入几次，不给总分排名，而是按任务阶段拆开看。判断：按阶段拆的评测才是团队选工具时需要的，它能对齐到你自己工作流里最容易出问题的那一段。别人说好用没意义，关键是它在最常做的那类任务上第几步开始掉链子。

<a id="20261123-05"></a>

### 5. Agent 的价值来自能改真实状态，不只是给建议

[查看原文](https://x.com/amasad/status/2124345037408686228) · 来源：Amjad Masad (@amasad)

Amjad Masad 谈 agent 在产品里的形态，强调让 agent 直接操作真实环境：文件、部署、运行结果，而不是在对话框里给建议。改不了状态的 agent 只是个更贵的搜索引擎。判断：能不能让 agent 安全地改状态，是接下来一年产品分化的地方，难的不是改，是改错了能收回来。

<a id="20261123-06"></a>

### 6. AI Infra 的机会在模型接入产品的中间层

[查看原文](https://x.com/garrytan/status/2124154280450134231) · 来源：Garry Tan (@garrytan)

Garry Tan 从创业和投资一侧讲 AI infra：机会不在模型训练，而在把模型接进产品的中间层，包括评测、路由、成本控制、延迟优化。很多团队现在卡在推理成本和延迟上，而不是能力上。这与一线体感一致：模型够用了，花钱和调优的部分才刚开始被人认真对待。判断：机会在成本和质量之间那条缝里，能把这条缝做窄的团队会有客户。

### 7. 团队换用新模型后的真实记录：哪些变好，哪些退步

[查看原文](https://x.com/danshipper/status/2124292892168475086) · 来源：Dan Shipper (@danshipper)

Dan Shipper 记录团队在日常工作里换用新模型后的实际感受，包括哪些任务变好、哪些反而退步。这类来自真实使用方的记录，比发布方的 demo 更能说明模型的实际边界。判断：模型迭代到现在，团队需要自己的一套小评测集，把常用的十来个任务固定下来，每次换模型跑一遍；跟着榜单换模型，最后只是把不稳定的部分换了个地方出现。
