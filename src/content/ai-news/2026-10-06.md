## 今日判断

今天我最想记下来的，是 Granola 联合创始人 Sam 那句关于 MCP 的坦白。他说团队一开始死活要把用户留在自己的 UI 里，后来发现企业客户内部工具太多，Granola 不跟这些工具配合就是死路一条，于是接受了：很多工作流里，Granola 最好的用法只是采集上下文，然后丢给客户自己的 agent 去干活。这不是一句产品哲学，这是一个真实的功能定位退让。我判断接下来会有越来越多工具产品接受自己变成 agent 链条上的一个数据节点，而不是最终界面。谁能早一点想清楚自己该交出哪一段，谁反而活得久。

第二条线是 Rauch 讲的 Rust 迁移复盘。他承认 Turborepo 从 Go 迁到 Rust 完成之后，内部 ROI 是很有争议的，人力迁移成本很高，Go 迭代快又好写。他真正想说的转折是：当写代码的人可能是 AI 而不是人，“最适合人类”不再等于“最适合业务”。这句话放在 coding agent 的语境里才成立，过去的语言选型几乎全是在赌人的招聘和迭代成本。我的判断是，编程语言、框架、甚至代码风格的选择标准，接下来两三年会被人机分工重新洗一遍，现在很多团队的工具链决策假设已经过期了。

还有一条更值得 builder 警觉的信号，是 Codex 那边说未来 28 天要么每天发一个对多数 codex/work 用户有明确改进的东西，要么就整段重置。这句话背后是一种承认：当前 harness 还没到位。配合 Rauch 说的模型越快、harness 开销越显眼，以及 ChatGPT 那边被吐槽 Work、Spaces、Codex 概念堆得太乱，我看到的共同问题是同一件事——这半年 Agent 产品的竞争已经从模型能力转到 harness 和产品结构上，谁把会话存储、检索、入口收敛这几件事做对，谁才留得住用户。模型领先的窗口在缩短，产品结构做错的代价在变长。

### 2. Rauch 复盘 Turborepo 从 Go 迁到 Rust：完成之后 ROI 内部争议很大

[查看原文](https://x.com/rauchg/status/2106863842450133114) · 来源：Guillermo Rauch (@rauchg)

Rauch 回应 Rust vs Go 的争论，讲了 Vercel 自己的经历：Turborepo 从 Go 迁到 Rust，迁移完成了，但内部对 ROI 争议很大，因为人力迁移成本非常实在，而 Go 本身够快、设计干净、迭代顺畅。他真正的新论点是：当写代码的人可能是 AI 而不只是人，原来“对人最友好”不再等于“对业务最友好”，所以语言和工具链的选择标准要重算。我认为这条对一线团队很有用，因为它把语言选型从审美和招聘问题，变成人和 agent 分工问题。接下来两三年，很多现有工具链决策的隐含前提会失效，尤其在 build 系统、编译器、低层基础设施这类同时服务人和 agent 的场景。

### 4. Rauch：模型越快，harness 开销越显眼，下一步优化会话存储与检索

[查看原文](https://x.com/rauchg/status/2106885457212825983) · 来源：Guillermo Rauch (@rauchg)

Rauch 说模型进一步提速之后，harness 的开销变得越来越关键。他提到下一个版本会改进会话存储和检索，并在 libfx 上解锁云端持久性。这条信息量不大，但机制清楚：模型推理越快，围绕它的调用、会话管理、状态读取这些外围成本占总延迟的比例就越高，优化收益也随之变大。我认为这是很多 agent 团队容易忽略的一点——大家还在追模型，但用户实际感受到的延迟和可靠性里有相当一部分是 harness 决定的。如果你的 agent 产品最近在做性能优化，会话状态的存取路径值得先量一遍，而不是先换模型。

### 5. Peter Yang：ChatGPT 该收敛了，Work 这个品牌本身可能就是个错误

[查看原文](https://x.com/petergyang/status/2106926956554195018) · 来源：Peter Yang (@petergyang)

Peter Yang 说 OpenAI 现在着手简化 ChatGPT 是对的，因为它已经变得很乱。他具体列了几组让人困惑的概念：Work 和 Codex、Spaces 和 Pages 和 Sites、模型和 effort 选择器。他的判断是 Work 整个发布是一次失误，因为 Work 不需要自己的品牌，就像 Claude 把 Cowork 收回 Chat 里一样。为什么重要——这反映的是通用 agent 入口的组织问题：多个相似能力被拆成多个品牌，用户每次都要先想清楚用哪个。我的判断是，做 agent 产品的团队应该把这条当成提醒，功能扩张期拆概念容易，但一旦用户要在多个入口间做选择，认知成本就开始拖转化，收敛比继续加更重要。

### 6. Aaron Levie：AI 带来的新岗位，很多是数据和研究岗被重新定位过去的

[查看原文](https://x.com/levie/status/2106893015063421357) · 来源：Aaron Levie (@levie)

Levie 说 AI 正在创造的新岗位已经开始显现：做应用 AI 产品的工程岗、进企业部署 agent 的 FDE、帮企业落地的服务公司。他还强调，公开统计低估了实际情况，因为大量原本做数据、研究、软件的企业岗位被重新定位去做 AI 相关工作，银行、生命科学、制造、律所都在增加技术人手或改造现有岗位来推进 agent 部署。为什么重要——这是为数不多讲清楚 agent 在企业里落地要靠哪类人力的一手观察。我的判断是，如果你在做 agent 基础设施或工具，FDE 和内部技术团队的部署体验会越来越值得当成产品重点，因为真正决定落地速度的是这批人的搬砖效率。

### 7. Rauch：README 手写给人看，内部文档用 AI 英语给 agent 看

[查看原文](https://x.com/rauchg/status/2106848085267902815) · 来源：Guillermo Rauch (@rauchg)

Rauch 分享他在做新项目时的一条实践规则：README 完全手写，因为它是给人看的，是讲故事、建立连接的地方；而文档内部的部分用 AI 英语写，因为那是给 agent 消费的。他认为这条规则能让世界更好，而且重点不在有没有 AI 味的标点，而在人类沟通场合要用人类语言。为什么重要——这给出了一个可立刻落地的分工判断，不是泛泛谈 AI 写作。我的判断是，随着 agent 越来越多地读你的仓库和文档，团队会逐渐分离两类文本：给人看的产品叙事和给 agent 看的结构化说明。越早把这两类分开写，越能同时保住产品表达和 agent 消费效率。

### 8. Dan Shipper：dot 成了我的主入口，但这层人格化外壳可能很快消失

[查看原文](https://x.com/danshipper/status/2106892868564431255) · 来源：Dan Shipper (@danshipper)

Dan Shipper 说他最近几周已经把 dot 当成主要 AI 入口，还给它起了名字 boo。他判断一年后自己可能还是用这种常驻、持久的 agent 方式与 AI 交互，但 boo 这个具体外壳大概会消失，就像早期 OpenClaw 时代大家喜欢那些个性特征，一旦有功能更强的选项就立刻换掉。为什么重要——这区分了两件容易被混为一谈的事：常驻 agent 的交互范式可能是持久的，但当前这一层的拟人化外观是临时的。我的判断是，做 agent 产品的团队不该过早把资源押在角色的个性营造上，真正决定留存的是功能上限；个性是加分项，但它挡不住功能更强的替代品。

### 9. Aaron Levie：消费级 AI 的那个指标，可能更多说明商业模式而非 AI 状态

[查看原文](https://x.com/levie/status/2106802940879192260) · 来源：Aaron Levie (@levie)

Levie 提出一个容易忽略的角度：某个被广泛引用的消费级 AI 指标，可能更多说明的是消费 AI 的商业模式，而不是 AI 本身的状态。他认为面向消费者的 AI 几乎必然会被补贴，并通过电商、广告或设备和服务销售来变现，所以这个指标可能比大家想象的更早走平。为什么重要——这提醒做产品和投资判断的人，别把用户增长类数字直接当成能力或需求信号。我的判断是，消费级 AI 的商业化路径会长期压制部分表面指标，真要评估需求，得看变现结构和留存质量，而不是单个使用量数字。
