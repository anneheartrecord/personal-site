## 今日判断

今天最值得注意的不是哪家又发了模型，而是"把 AI 接进真实业务"这层正在被认真当成一门工程来做。Aaron Levie 那套部署层说法听起来像常识，但拆开看每一条都是真实的苦活：老系统上云、数据权限重做、软件用新方式接 agent、流程为 agent 重排、人机协作边界、eval 持续维护，还有模型一升级整套系统就得跟着动。这跟装普通软件完全是两回事，我给它的权重比任何一条模型发布都高。

另一条线是 agent 协作界面的收敛。Peter Steinberger 说他把 harness 里 agent 之间的通信改成默认折叠成一行，我很有共鸣：agent 一多，chat stream 就会糊成一锅粥，谁在跟谁说话、哪条是有效上下文都看不出来。Garry Tan 看到的 Capy 让 agent 互为 peer 自己协调、而不是从上往下派活，是另一种思路。这两个方向不冲突，一个管可读性，一个管探索空间，最终都会影响你怎么设计 agent 的默认工作流。

基础设施层的信号也很清楚：Thibault 说 GPT-6.1 Sol 是有史以来需求最大的模型，正在加容量；同一个人紧接着宣布能在 ChatGPT 里直接建和部署 MCP server 并控制访问权限。MCP 从协议变成产品内建能力，意味着接工具这件事的门槛又降了一截。Guillermo 那条关于 token aggregator 噪音和 ZDR 的吐槽，是给选 provider 的人提个醒：别只看价格和数量，看真实用量和合规。

### 1. Aaron Levie：AI 进企业的真正难点在部署层

[查看原文](https://x.com/levie/status/2105354449795621179) · 来源：Aaron Levie (@levie)

Levie 指出当前最大的机会是做 AI 进入经济体的部署层，因为改造企业工作流的实际工作量远超所有人预期。他列了一份清单：遗留系统上云、数据组织和访问权限更新、软件用新方式接入 agent、为 agent 重新设计工作流、确定人在环中的位置、生成并维护 eval、以及随着新模型和新能力出现持续更新整套系统。他强调 AI 不等于部署软件，普通软件实施完就基本定型，而 AI 系统需要持续演进。我的判断是，这份清单本身就是很多 AI 产品路线图应该对照的 checklist，谁在部署层把这七件事做成可复用的产品和服务，谁就能吃到企业预算里最大的一块。

### 2. OpenAI 的 Thibault：GPT-6.1 Sol 需求空前，正在加倍扩容

[查看原文](https://x.com/thsottiaux/status/2105464274747527543) · 来源：Thibault Sottiaux (@thsottiaux)

Thibault 表示 GPT-6.1 Sol 是 OpenAI 有史以来在 API 和订阅两端需求都最大的模型，ChatGPT 和 Codex 都承受了重负载，目前已经上线更多容量，未来数小时速度会明显改善，接近前一天的两倍。这条信息本身很短，但对正在跑 Codex 或调 API 的 builder 很实际：你不是一个人在抢算力，官方的应对是加容量而不是降能力。我的判断是，模型发布后的头几天容量和速度波动应该被当作默认预期写进工作流，关键任务不要卡在首发窗口，同时可以关注官方扩容节奏来判断真实需求规模。

### 3. ChatGPT 内可直接构建和部署 MCP server，并可控制访问权限

[查看原文](https://x.com/thsottiaux/status/2105519215092584786) · 来源：Thibault Sottiaux (@thsottiaux)

Thibault 宣布用户现在可以直接在 ChatGPT 里构建和部署 MCP server，并能把访问权限限制给指定的人，或公开分享给所有人。这条的分量在于它把 MCP 从需要一个外部开发环境的事情，变成了产品内的默认能力，同时顺带解决了权限控制。我的判断是，接工具的门槛会再降一档，很多小团队会直接把内部工具包一层 MCP 挂进来，而权限粒度会成为区分企业可用和玩具的关键。接下来值得观察的是，这种内建 MCP 和自建 server 在鉴权、审计、版本管理上会怎么分化。

<a id="20261002-04"></a>

### 4. Peter Steinberger：agent 之间通信默认折叠成一行

[查看原文](https://x.com/steipete/status/2105362785534361996) · 来源：Peter Steinberger (@steipete)

Steinberger 说他越来越受不了 chat stream 里 agent 之间的通信刷屏，于是把 harness 里的可见性改成默认只显示一行、需要时可以展开。他还判断其他人会跟进这个做法。这是个很小的改动，但指向一个真实问题：多 agent 系统一旦跑起来，上下文流会迅速变成噪音，人没法判断哪条是有效信息。我的判断是，agent UI 的下一步不是展示更多，而是默认收起、按需展开，把噪音当默认，把细节放抽屉里。做 coding agent 或任何多 agent 界面的人，这个默认值值得直接抄。

<a id="20261002-05"></a>

### 5. Garry Tan：Capy 让 agent 像同辈一样互相协调

[查看原文](https://x.com/garrytan/status/2105449821645480046) · 来源：Garry Tan (@garrytan)

Garry Tan 说别的代码编辑器都是自上而下地协调子 agent，而 Capy 里 agent swarm 像同辈一样互相对话、自己协调，让你有机地探索空间，而不是预先安排好一切。他用了 special 这个词。我的判断是，这两种模式的差别不只是实现，而是产品哲学：自上而下适合确定任务，peer 式协调适合探索式任务。真要做后者，难点会落在冲突解决和状态收敛上，谁先把这块做稳，谁就能拿到探索式 agent 的场景。

<a id="20261002-06"></a>

### 6. Guillermo Rauch：token aggregator 噪音大，ZDR 不能只听承诺

[查看原文](https://x.com/rauchg/status/2105476587756138942) · 来源：Guillermo Rauch (@rauchg)

Rauch 说大多数 token aggregator 充满噪音，一是训练你数据的 provider 在互相导量推广，二是自称零数据保留但未必可信的 provider。他称 Vercel AI Gateway 基于 40 万付费用户和数千企业的真实用量、零加价，是理解全球 token 流向的可信数据源。他还说每周都拒绝一些打着免费 token 旗号、ZDR 声明可疑的公司。我的判断是，选 provider 时不要被"最多供应商"迷惑，ZDR 要能验证，最烂的 provider 混进来会直接变成合规负债。对做 infra 采购的人来说，真实用量加法律合规投入比价格表重要。

### 7. Sam Altman：开发者的门槛在提高，但需求和岗位都没消失

[查看原文](https://www.youtube.com/playlist?list=PLuMcoKK9mKgHtW_o9h5sGO2vXrffKHwJL) · 来源：AI & I by Every

在这期节目里，Sam Altman 说四年前如果有人告诉他 coding 模型会到这个水平，他可能会觉得 Dev Day 上开发者会变少，但现实是开发者比以往更多、要做的事也更多。他的解释是人们想要的东西太多了，期望水涨船高，开发者能做的一直在变多，但标准也在提高。他还提到低估了世界上潜在需求的规模，以及人在整个 AI 进程中的中心位置。我的判断是，这段话的重点不是乐观情绪，而是标准抬高这个机制：工具让产出更快，同时把及格线也推上去了，一线 builder 要习惯每半年重估一次什么叫做完。

### 8. Google Labs 关停 Opal，把能力沉淀进 Gemini Skills 全球上线

[查看原文](https://x.com/GoogleLabs/status/2105352889665564838) · 来源：Google Labs (@GoogleLabs)

Google Labs 宣布 Opal 的实验将于 2026 年 11 月 17 日关停，而从 Opal 学到的经验变成了 Gemini App 中 Skills 的全球上线。Skills 是一种更快的自动化重复任务方式，可以把自定义指令直接保存在聊天里。我的判断是，这件事说明大厂在把"自定义工作流"从独立实验产品收回进主应用：独立实验利于学习，但留存和分发放进主入口更划算。对做类似能力的小团队来说，这是个信号：自定义指令和自动化如果没绑在主要对话入口上，很容易被主产品顺手吃掉。
