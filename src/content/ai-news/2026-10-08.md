## 今日判断

我今天最关注的一条是 Boris Cherny 讲的 prompt 方式。他说现在给 Claude 写 prompt 别搞太多脚手架，核心就三件事：告诉它要做什么、愿意花多少力气、怎么验证自己做对了。这句话信息量在于它是对着一个强模型的真实使用经验，不是教条。我的判断是，prompt engineering 正在退化成任务定义一个，重点从怎么写句子转到怎么定义验收标准。你如果还把精力放在提示词模板上，可能在浪费力气，不如把验证机制写清楚。

第二条我关注 Peter Steinberger 的团队 claw。他把团队 agent 接到 X 上触发任务，未分配的会话谁都能领，agent 看代码历史找相关人并 ping，整套东西是一个 prompt 加可热重载插件扩出来的。这值得记，因为它展示了一种很具体的团队协作形态：agent 不是替人写代码，而是替人分派和路由工作。我判断这种松散、可热插拔的团队 agent 会越来越多，真正的门槛不在模型，在于你有没有把团队工作流做成 agent 能读的结构。

还有一条是 Thariq 说的云端大脑加本地手。他说的技术细节很实：如果 Claude 只能在你电脑在线时访问文件，那它会被卡住，所以需要某种同步，但同步又有边界情况。我看下来这基本就是接下来一年 coding agent 的架构方向，模型在云上跑，本地只留执行和文件触达。对 builder 的提醒是，别急着做一个全部本地的方案，云加本地的混合架构才是主流，先想清楚你的同步和权限边界。

### 1. Boris Cherny：现在的 prompt 就三件事

[查看原文](https://x.com/bcherny/status/2107565388250874193) · 来源：Boris Cherny (@bcherny)

Boris Cherny 说别再对 prompt 感到惊讶，跟 Claude 说话就像跟同事说话。他不认为 prompt 有什么秘密，大多数任务不需要过度脚手架或规定死步骤，给个目标让 Claude 自己去想办法。他特别指出 Sonnet 3.5 时代 prompt 很重要，现在真正重要的是三件事：告诉模型你要它做什么、你希望它花多少力气、它该怎么验证自己做对了。为什么重要：这等于承认 prompt 写法的重心已经从措辞转向任务定义和验收标准。我的判断是，builder 该把精力从攒提示词模板转到设计验证回路，能把验收条件写清楚的人，用 agent 的差距会越拉越大。

### 2. Peter Steinberger：把团队 agent 接进 X，让会话自己找人

[查看原文](https://x.com/steipete/status/2107697554448421160) · 来源：Peter Steinberger (@steipete)

Peter Steinberger 把团队 agent claw 接到 X 上，用来更快触发工作。未分配的会话任何人可以领取，agent 会查谁最近改过相关代码，然后在服务器上 ping 对应的人。他说整个东西就是一个 prompt，团队服务器自己扩出来的，因为插件现在可以热重载。为什么重要：这是 agent 作为团队工作路由器的具体例子，不是替人写代码，而是替人分派、找人、追上下文。我的判断是，这种可热插拔的团队 agent 会先在小团队落地，门槛不在模型能力，在于你有没有把代码历史和工作流做成 agent 读得懂的结构。

### 3. Thariq：云端大脑加本地手，是 coding agent 的下一段架构

[查看原文](https://x.com/trq212/status/2107580785456976085) · 来源：Thariq (@trq212)

Thariq 说方向越来越清楚：Claude 的大脑在云上，然后给 Claude 本地的手去操作你的电脑。他在后续回复里补了具体技术难点：如果 Claude 只能在你电脑在线时访问文件，那它可能被卡住直到电脑重新开机，所以需要某种同步，但同步又有边界情况要处理。为什么重要：这是 coding agent 从纯云端或纯本地走向混合形态的一个明确信号，本地负责文件和执行，云端负责推理。我的判断是，做这类产品的 builder 不要急着赌全本地，先想清楚同步策略和权限边界，因为在线状态会直接决定 agent 能不能连续干活。

<a id="20261008-04"></a>

### 4. Thariq：抽象层级越高，越要懂底层

[查看原文](https://x.com/trq212/status/2107504677143368163) · 来源：Thariq (@trq212)

Thariq 说在更高的抽象层级上工作，一直都需要理解更低的层级，他不认为 coding agent 会改变这一点。为什么重要：这是对懂不懂底层在 agent 时代还有没有意义这类讨论的一个干脆回答。我的判断是，agent 帮你把实现细节推远之后，真正的差距会回到你能不能判断哪一层出问题、哪一层该改。底层能力没有被取消，只是换了一种用法，从写变成诊断。对带团队的人来说，这意味着招人和培养的重心要放在系统判断力上，而不是语法熟练度。

### 6. Every 团队把公司 agent 做成 Slack 里的共享技能层

[查看原文](https://x.com/claudeai/status/2107574195978641911) · 来源：Claude (@claudeai)

Claude 官方介绍 Every 团队的用法：他们让尽可能多的工作跑在 agent 上，为了在新模型出现时让全团队共享技能，基于 Claude Managed Agents 做了一个公司 agent，所有人都在 Slack 里用。内部火了之后，他们把它开放给了订阅者。Dan Shipper 补充说没有 Claude Managed Agents 就做不出这个 agent。为什么重要：这展示了一种团队层面的 agent 形态，不是个人助手，而是共享能力层，新模型来了大家能一起升级。我的判断是，把 agent 做成组织内共享的基础设施、而不是每人私藏一堆脚本，会是接下来小团队拉开效率差距的地方。

### 7. Aaron Levie：安全会成为 AI 落地的主战场之一

[查看原文](https://x.com/levie/status/2107680435644039269) · 来源：Aaron Levie (@levie)

Aaron Levie 说未来几年网络安全会是 AI 最具决定性的领域之一，也是多数企业的重点。AI 会制造一批新的安全工作：vibe coded 留下的问题、agentic 攻击、甚至意外失控的 agent 群在到处找数据。他说安全团队本来就是企业里资源最紧的，现在只会更紧。同时 agent 本身也是解法，会出现保护代码、企业系统、关键基础设施和数据的 agent 产品。为什么重要：他把 agent 普及和安全工作量直接挂上钩，说的是具体机制而不是泛泛的风险论。我的判断是，做企业 agent 的 builder 要把权限和审计当成产品的一部分，而不是上线后再补。
