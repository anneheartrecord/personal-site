## 今日判断

今天最值得看的不是哪家模型又刷了榜，而是几条关于「agent 产品到底怎么做」的一线手感。Nikunj 说 tokenmaxxing 最凶的公司往往产品体验最差，因为好产品靠 curation 和 gardening，不是把厨房水槽全扔给 agent 让它自己猜。这话听着像吐槽，其实点出了当前 agent 产品分层的核心机制：上下文喂什么、什么时候停、哪些步骤该确定性代码兜底，这些手工打磨的活才是体验差距的来源。Garry Tan 提到的 Capy 能在多步 workflow 和大型 PR 上比 Codex、Claude Code 单独跑更快，也印证了同一个方向——赢家可能在编排和任务切分上做对了，而不是单模型能力领先。

第二块我盯的是 agent 从「辅助人」变成「替人执行」之后，基础设施会发生什么。Aaron Levie 算过一笔账：agent 用软件的频率会是人力的 100 倍，而且越来越多的任务里 agent 会直接产生副作用，这就让权限、审计、回滚、数据边界这些过去藏在后台的 primitive 变成决定 workflow 能不能跑通的东西。Peter Yang 那条广告市场的推论是同一枚硬币的另一面：如果 agent 替人把事办了，人根本没看到展示广告，那现有一大块商业模式会被静默重定价。这不是遥远的假设，browser use 和 computer use 已经在真实发生。

我的判断给一线 builder：接下来半年值得花时间的不是再包一层聊天壳，而是把「agent 能安全执行到什么程度」这件事做深。具体就是任务切分、失败恢复、副作用审批、以及压缩上下文而不是堆上下文。谁的 agent 能在多步真实 workflow 里稳定收敛，谁就拿到下一轮的产品定义权；只靠堆 token 和堆工具数量的团队，会先感受到用户流失。

### 1. Nikunj：Codex 在 Mac 上的 Computer Use 目前没有对手

[查看原文](https://x.com/nikunj/status/2102186665863463199) · 来源：Nikunj Kothari (@nikunj)

Nikunj Kothari 说他长期把 Codex 当主力 agent 用，以至于忘了普通人根本没用过这类工具。他认为 Instinct 和 Muse 对手机浏览场景做得不错，让大众零配置就能体验好 agent；但 Codex 在 Mac 上的 Computer Use 能力目前「不可战胜」，直接把手动 workflow 丢给它做 one-shot 就能跑通。他还提到 OpenAI  reportedly 准备把 agent 推向大众，自己的唯一建议是展示真实工作并降低上手门槛。我关注这条是因为它是一个重度用户给出的产品分层判断：面向大众的零配置 agent 和面向专业工作流的 computer use agent 会是两条不同的产品曲线，前者拼普及，后者拼能真正接管多少手动操作。对做 agent 产品的人来说，这里有个可验证的问题——你的 agent 在手机浏览和桌面接管两个场景里，到底解决了哪一类人、哪一类任务。

### 2. Garry Tan：Capy 在多步 workflow 和大型 PR 上比 Codex、Claude Code 更快

[查看原文](https://x.com/garrytan/status/2102095924893827501) · 来源：Garry Tan (@garrytan)

Garry Tan 说他最近一周最爱的 agentic coding 秘密武器是 Capy，他不确定 Capy 具体怎么做到的，但它在跟踪多步 workflow 和执行大型 PR 上比 Codex 或 Claude Code 单独跑更快。他随后补充了一个例子：在 GBrain 上一个很激进的 bug fix wave 中，Capy 做到了清晰的任务切分、自动并行化，以及干净的 GitHub PR 和 CI 流程。这条的价值不在谁快谁慢的结论，而在于它指出了一个机制——当任务被切分成边界清楚的子任务并自动并行时，整体吞吐会明显超过单 agent 串行执行。对正在做 coding agent 或内部开发工具的人来说，值得拆的是任务切分粒度和并行协调怎么设计，而不是只盯模型能力对比。

### 3. Nikunj：tokenmaxxing 最凶的公司，产品体验往往最差

[查看原文](https://x.com/nikunj/status/2102049065504739366) · 来源：Nikunj Kothari (@nikunj)

Nikunj 说，除了少数例外，那些吹嘘自己在 tokenmaxxing 的公司，产品体验反而是最差的。他的解释是，好产品靠的是 curation 和 gardening，不是把厨房水槽全扔给 agent 然后期待它自己搞明白，less is more 在 agent 时代比任何时候都成立。这条重要是因为它把「堆 token、堆工具、堆上下文」和「体验好」之间的因果讲反了：更多输入并不自动带来更好结果，反而会增加模型在无关信息里漂移的概率。我的判断是，接下来 agent 产品的分水岭会出现在上下文选择、工具精简和失败边界设计上，而不是谁接的模型更多。做 agent 的团队如果把 token 消耗量当健康指标，很可能正在掩盖产品体验的真实问题。

### 4. Aaron Levie：agent 用软件是人力的 100 倍，primitive 反而更重要

[查看原文](https://x.com/levie/status/2102235949430354273) · 来源：Aaron Levie (@levie)

Aaron Levie 判断 AI agent 会以人类 100 倍以上的频率使用软件。即使界面逐渐退到后台、人主要通过 agent 交互，那些核心 primitive 依然被需要，而且在 agent 能执行破坏性操作、其访问的上下文能决定 workflow 成败的场景里，这些 primitive 反而变得更关键。他具体指向 CRM、ERP、结构化和非结构化数据平台，认为能充当 agent 安全层、为人与 agent 管理数据、并编排业务逻辑的平台有很大机会，新创业公司和能快速行动的现有平台都包括在内。我关注这条是因为它把 agent 竞争从模型层拉回到企业软件的权限、审计和业务逻辑层。对 builder 来说，这意味着机会不只是做更好的 agent，还包括做 agent 愿意调用、企业敢放权的下层接口。

### 5. Peter Yang：agent 替人办事后，展示广告市场会被静默重定价

[查看原文](https://x.com/petergyang/status/2102215701255844074) · 来源：Peter Yang (@petergyang)

Peter Yang 提出一个可能被低估的冲击：如果一家公司很大一部分收入来自向人类展示定向展示广告，那么当 agent 替用户浏览网站并把事情直接办完、人根本没有看到广告时，会发生什么。他把这称为广告市场可能面临的 rude awakening。这条值得关注，因为它把 agent 的能力从工具效率问题推到了商业模式层面。机制上很清楚：展示广告按人类注意力计价，而 agent 执行任务时分不出注意力给广告位，一旦 agent 流量占比上升，现有转化路径和计费基础都会被稀释。我的判断不是广告会消失，而是未来一两年以广告为主要变现的产品需要提前想清楚，当用户侧越来越多由 agent 代理时，你的价值捕获点放在哪一层。

<a id="20260923-06"></a>

### 6. Aaron Levie：个人 agent 替人交易，会带出一个新的商业层

[查看原文](https://x.com/levie/status/2102253246807261579) · 来源：Aaron Levie (@levie)

Aaron Levie 认为能替用户完成交易的个人 agent 有可观的变现潜力。他的推演是：用户先会拿 agent 处理日常琐碎烦人的任务，习惯之后开始丢更复杂的任务，最终通过 agent 发生的消费会比过去更多，因为摩擦降低本身就会刺激支出。这给 agent 提供方带来机会，也给围绕 commerce、本地服务、B2B 服务构建「agent 想调用的那一层」带来全新机会，他判断这是多层共赢。我关注的是他隐含的机制：降低交易摩擦会把原本不会发生的需求释放出来，而不是简单替换现有渠道。做 agent 产品的人要问的是，你的 agent 在替用户完成交易时，和哪些服务层的接口、权限和信任关系最值得提前建设。

### 7. Peter Steinberger：Meta 自建 agent 受 OpenClaw 启发，但不是直接用

[查看原文](https://x.com/steipete/status/2102116206371315854) · 来源：Peter Steinberger (@steipete)

针对正在流传的「Meta 使用 OpenClaw」说法，Peter Steinberger 澄清：Meta 是受启发后自建了自己的 agent，Nat 和团队做得很好。这条价值在于它既纠正了一个被反复转发的错误信息，也暴露了一个真实模式——大公司看到开源或外部 agent 方案后，往往会选择内部自建而不是直接采用，原因通常是安全、合规和数据边界。对做开源 agent 或 infra 的团队来说，这意味着被大厂「看见并借鉴」和「被大厂采购」是两件不同的事。我的判断是，和大公司的合作路径更适合定位成参考实现或内部加速器，而不是期待他们直接接入你的生产系统。

### 8. Guillermo Rauch：AI Gateway 新增通过 HTTP 使用 Jev

[查看原文](https://x.com/rauchg/status/2102205684544852121) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 宣布，除了类型安全的 AI SDK API，现在也可以在 AI Gateway 中通过 HTTP 使用 Jev。这条信息量不大，但属于实际的产品能力更新，指向一个稳定趋势：模型接入层正在把多 provider、类型安全和网关能力合并成一个标准入口。对正在构建多模型应用或 agent 的团队来说，值得关注的是接入方式从 SDK 延伸到 HTTP，意味着非 JS 技术栈和更轻量的调用场景也能走同一套网关。我的判断是，AI 网关这类中间层的竞争会集中在切换成本、可观测性和调用规范上，单纯做代理转发很难形成壁垒。

### 9. Peter Yang：ChatGPT Finances 已经在替用户追回错扣款项

[查看原文](https://x.com/petergyang/status/2102186174911746151) · 来源：Peter Yang (@petergyang)

Peter Yang 分享 ChatGPT Finances 的产品负责人 Ethan 的案例：他用积分订了酒店但被重复计费，自己没发现，ChatGPT 发现后联系客服并帮他拿回了退款。Peter 也说了自己的类似经历，让 ChatGPT 取消父母的酒店预订、监控回复并持续跟进直到退款到账。这条值得看的地方在于，agent 做的不是回答问题，而是发现异常、发起沟通、跟踪直到结果闭环。机制上是把过去需要人反复 check 的客服流程整段代理出去。我的判断是，财务和客服这类有明确状态和可验证结果的场景，会先跑通端到端 agent，因为它比开放式任务更容易定义成功并加入人工确认点。
