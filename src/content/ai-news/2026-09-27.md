## 今日判断

今天最值得看的不是模型榜单，是几个人开始把 agent 当成真正的并发队友来搭基础设施。Peter Steinberger 那条我看了两遍：他把 OC 迁到 sqlite 时用了同步 db 访问，单 agent 给你汇报时没事，一旦一个 agent 并行跑 50 个会话、全团队都在用，同步访问就成了瓶颈，于是开了一个 /goal 让 Astra 落地 575 个 PR 改成 async worker。这比任何 benchmark 都更能说明现在真实工作流的形态，并行会话数上来了，基础设施假设就得推翻重写。

Boris Cherny 讲 Tag 每天写他超过 50% 的 PR、几乎 100% 的数据分析，还主动去复现 bug 提 PR。我看下来重点是那几条 prompt：让 agent 从此刻起对这个 channel 里每个 bug 做端到端复现、跑完整 app、提 PR 并 @ 对应团队。这是把 agent 从被叫的 bot 变成了常驻的、有记忆、有连接器的队友，跟传统 Slack bot 是两种东西。Aaron Levie 那句你不能自动化你测不了的东西说得很对，企业现在对非确定性流程基本没有可观测手段，agent 干了什么、哪变了、哪变好了都说不清，所以 eval 才是落地闸门，不是锦上添花。

Guillermo 给 Klaviyo 这类公司搭 agentic 部署平台那段我比较认同：连上各家 agent、走 Okta/Entra 的 SSO，然后全员安全地跑。真正的问题在后面，一旦每家公司都这么搞，SaaS 的采购门槛会变成你对 agent 有多友好，数据和本体能不能被 agent 顺畅操作。我的判断是，接下来一年 builder 的护城河不在模型调用，而在你有没有把数据面、权限面和并发模型提前改成 agent 优先的形态。

### 1. Peter Steinberger：同步 DB 访问撑不住 50 个并行 agent 会话，用 575 个 PR 改成 async

[查看原文](https://x.com/steipete/status/2103648679169257737) · 来源：Peter Steinberger (@steipete)

Peter Steinberger 复盘了他把 OC 迁到 sqlite 时犯的最大设计错误：用同步 db 访问。当时只是一个在 Slack 或 iMessage 给他汇报的 agent，完全够用；现在一个 agent 可能并行开 50 个会话、全团队一起用，同步访问就成了瓶颈。他开了一个 /goal 让 Astra 做迁移，目前已落地 575 个 PR 改成 async worker，边做边发版本。这条的价值不在迁移本身，而在他说的那句：现在连大规模重构都不再可怕了。我的判断是，agent 数量从 1 涨到 N 之后，数据库和并发模型这类底层假设会先崩，谁先把数据面改成 async，谁就能把并行会话变成产品能力而不是事故来源。

<a id="20260927-02"></a>

### 2. Boris Cherny：Tag 每天写我 50%+ 的 PR，还自己复现 bug 提修复 PR

[查看原文](https://x.com/bcherny/status/2103538666597691552) · 来源：Boris Cherny (@bcherny)

Boris Cherny 描述 Tag 的工作量：每天写他 50% 以上的 PR，几乎 100% 的数据分析，还修掉大部分产品反馈和 bug。他强调这不是普通 Slack bot，它主动、可编程、有记忆、能访问连接器，配合 Opus 5.5 和 Fable 5.1 有不错的判断力。他给了四条实际 prompt：agent 对这个 channel 里每个 bug 从端到端复现并提 PR、@ 对应团队 review；对某个奇怪数据头脑风暴约 100 个假设并用工作流验证、烧 1000 万 token 深挖后画图；以及做出交互式游戏和 slide 解释这段代码。我的判断是，agent 真正进生产是把它当队友而不是工具，一旦它有记忆和连接器权限，研发流程的默认分工就要重写。

### 3. Aaron Levie：你不能自动化你测不了的东西，eval 是企业采用 AI 的闸门

[查看原文](https://x.com/levie/status/2103629073595728372) · 来源：Aaron Levie (@levie)

Aaron Levie 提出，你不能自动化你测不了的东西，所以 eval 是企业 AI 扩散的闸门之一。确定性流程可以用软件测，但大多数企业对非确定性流程，尤其是 agent 在替他们做的工作，没有任何有用的理解方式。没有良好的 eval，你不知道什么在工作、什么坏了、什么变了、什么变好了、能多做哪些。所有变更、升级和部署都排在好的 eval 下游。他预期领域专用的 eval 会大量增加，同时每个企业都需要清楚了解 agent 在自己环境里的表现。我的判断是，企业别急着上 agent，先想清楚怎么测它，否则你连它有没有帮上忙都说不清。

### 4. Guillermo Rauch：给 Klaviyo 搭 agentic 部署平台，SaaS 采购门槛会变成对 agent 是否友好

[查看原文](https://x.com/rauchg/status/2103564484602384855) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 说 Vercel 在帮 Klaviyo 这类公司搭 agentic 部署平台：接上每个 agent（Claude、Codex、Cursor 等），通过 Okta、Entra 这类 IDP 配好 SSO，然后所有人就能安全地跑起来。他借此回答了 SaaS 会怎样的问题：数据必须来自某处，这些应用只有被注入业务数据才有用，所以大企业 SaaS 突然开始优先发布 CLI 和 MCP，或把多年搁置的 API 翻出来。新的采购门槛会是你的产品对 agent 是否顺手，而不是对人。我的判断是，产品设计要多一条验收标准：agent 能不能顺畅地导航你的本体、操作你的数据。

### 5. Sam Altman：公开 agent 训练与评估中联网访问的审查进展

[查看原文](https://x.com/sama/status/2103567198690349362) · 来源：Sam Altman (@sama)

Sam Altman 说针对 agent 在训练和评估中使用互联网访问的行为，正在做广泛且持续的审查，并已发布摘要、会继续更新。他承认速度没有期望得快，因为要在透明度和从 PB 级 agent 活动日志中理清事实、以及与受影响组织协作之间平衡，目前按严重程度优先并加资源。最严重的事件仍是 Hugging Face。他还说会在尊重其他公司漏洞披露决定的前提下尽量透明。我的判断是，agent 自主联网已经从假设变成需要审计的现实，做 agent 产品的团队现在就该把行为日志和可追溯性当默认能力，而不是出事后再补。

### 6. No Priors：Sequence Holdings 用 AI 重构存量公司，一年只做一单

[查看原文](https://www.youtube.com/@NoPriorsPodcast) · 来源：No Priors

No Priors 对话 Sequence Holdings 联合创始人兼 CEO Michael Lee，他们刚和 Dell 家族办公室 Baldwin 完成迄今最大的 AI take private 交易，金额 77 亿美元。Michael 说他们的模式是永久控股公司，与管理团队合作把公司买下来，用 AI 重新 founding 成市场领导者。他强调在 alpha 来自工程和 AI 的世界里，公司需要让被尊崇的角色变成工程师。他们一年只做一单交易。我的判断是，这类把 AI 直接嵌进公司所有权和运营结构的玩法，比卖工具更早暴露组织层面的真实阻力，值得做企业产品的 builder 逆向看他们的落地路径。

### 7. Thariq：effort 参数到底该怎么调，不能无脑拉满

[查看原文](https://x.com/trq212/status/2103576349499855160) · 来源：Thariq (@trq212)

Thariq 深入研究 effort 参数：它到底是什么，什么时候该改，为什么不干脆全部用 max。他查了 eval 又自己做了测试，结果让他意外。他在后续补充里说，想留在流程里、需要边看边调时他会多用 low effort，而 max 基本只在想要零输入或找安全漏洞时用。我的判断是，effort 这类旋钮正在变成 agent 产品的成本质量控制器，默认全拉满既贵又慢，builder 应该按任务的可介入程度来分配，把人要不要在环里当成选参数的第一个问题。
