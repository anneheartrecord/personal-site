## 今日判断

我今天最在意的不是某条模型发布，而是 Vercel 给出的那组流量数据：全站 58% 的流量来自 bot，60% 以上的部署是 agentic，文档站 83% 的访问来自 agent。这不是趋势预测，是已经发生在自己基础设施上的事实。谁在为 agent 优化内容、为 agent 提供 CLI 和 API 入口，谁就在把分发渠道重新铺一遍。Guillermo 让 agent 直接在 marketplace 买基础设施甚至注册域名，本质上就是这个逻辑往前推了一步——agent 开始成为客户。

第二件事是定价逻辑被摊开讲清楚了。Madhu 那串拆解值得记下来：单位智能的价格下行不是开源模型带来的，而是蒸馏、推理效率、供应商竞争三件事并行。中杯模型的智能等于上一代大杯，同样智能更便宜的钱，这个节奏会持续。做产品的人如果不把这条曲线当成默认前提来设计成本结构，很容易在毛利上被打穿。

还有一个体感是 agent 的使用方式正在从对话框里走出来。Aaron Levie 说 agent 生成的 agent、后台持续跑的 agent 会消耗比人手动 prompt 多一千倍的 token，我认同这个方向；Thariq 那条 side project 从 Agent SDK 迁到 Managed Agents 后稳定性的变化，是这条判断的具体版本。我的结论是：接下来一年，评价一个 AI 产品好不好，不该看它对话多聪明，而要看它有没有把常驻进程、状态管理、失败恢复这些脏活做掉。

### 1. Vercel 自曝流量结构：58% 是 bot，60% 以上部署来自 agent

[查看原文](https://x.com/rauchg/status/2108733051283050964) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 公布 Vercel 网络的几个数字：过去 30 天全站 58.18% 的流量由 bot 发起，2024 年 1 月这个比例是 32%；现在 60% 以上的部署是 agentic，今年 1 月还只有约 3%；Vercel 自家文档站最高有 83% 的页面访问来自 agent，而且内容越针对 agent 优化，这个比例越稳定上升。他还判断人类直接访问互联网流量未来会变成零头。这条重要的地方在于它把 agent 流量从话题变成了可测量的运维指标——如果你的文档、CLI、API 首页不是为 agent 设计的，你正在丢掉大部分真实访客。我的判断是，接下来做开发者产品，agent 可读性会和 SEO 一样进入排期，而且优先级更高。

### 2. Vercel 让 agent 直接在 marketplace 买基础设施，还能注册域名

[查看原文](https://x.com/rauchg/status/2108669027363295323) · 来源：Guillermo Rauch (@rauchg)

Guillermo 说 Vercel 已经被 agent 通过 CLI 在 marketplace 采购基础设施产品的频率惊到了，现在把这条链路扩展到域名：agent 可以直接从想法走到上线一个带域名的生意，全栈闭环。这件事的分量不在域名本身，而在于 agent 第一次成为真实的付费客户——它们会挑服务、比价格、走结算流程，甚至持有资产。对做 API、CLI、计费系统的人来说，这意味着要重新考虑面向 agent 的产品形态：人类看的落地页不再是唯一入口，机器可读的定价、配额、错误语义才是。我的判断是，谁先把 agent 当客户做，谁就能吃到下一波分发红利，因为人类获客成本只会更贵。

### 3. Aaron Levie：agent 后台常驻工作会把 token 消费推高 1000 倍

[查看原文](https://x.com/levie/status/2108750943680630893) · 来源：Aaron Levie (@levie)

Levie 的观点是：agent 派生 agent、后台持续处理任务、agent swarm 会消耗比人工逐条 prompt 多 1000 倍的 token。现在把 AI 当成聊天系统、只在你打字时才工作，一两年内就会显得过时；绝大多数 token 会由在后台和你的工作流里持续干活的 agent 消耗掉。这正是他现在看 agent 采用曲线还非常早期的原因，也是还需要更多算力和基础设施投入的原因。这条对做 Infra 和成本模型的人有用：预算不该按人头和会话数算，要按常驻 agent 数和它们之间的调用扇出来算。我的判断是，agent 中间件、调度、配额治理会是接下来最缺人的地方。

<a id="20261011-04"></a>

### 4. Madhu Guru：开源模型没开启降价，它只是顺风

[查看原文](https://x.com/realmadhuguru/status/2108618266776387886) · 来源：Madhu Guru (@realmadhuguru)

Madhu 指出，单位智能价格的下降不是开源权重模型引发的，开源只是已经发生的趋势上的顺风。真正推价格往下的是三件事：模型厂把最强模型蒸馏成更小的版本、推理侧的效率提升、以及模型供应商之间的竞争。这个模式在每个模型公司都能看到——中杯第 x 版的智能，等于上一代大杯；同样的智能，花更少的钱。这条的价值是给做产品的人一个可操作的默认假设：不要把当前推理成本当常数写进商业模型，要按代际下降预留空间。我的判断是，定价页里按 token 线性收费的产品，会最先被这条曲线压毛利。

### 5. ChatGPT 订阅现在等同于一份 Devin 订阅

[查看原文](https://x.com/thsottiaux/status/2108777962053292398) · 来源：Thibault Sottiaux (@thsottiaux)

Thibault 一句话宣布：你的 ChatGPT 订阅现在同时是一份 Devin 订阅。这条信息很短，但对做 coding tool 的人冲击不小——主流订阅一旦把 agent 编码能力包进去，独立 coding agent 的单独收费逻辑就被挤压。同时它也说明 OpenAI 在把订阅变成 agent 能力的通用入口，而不是单一聊天产品。我的判断是，接下来 coding agent 的竞争会从能力竞争转向捆绑与配额竞争：谁的订阅里能塞进更多后台 agent 时长、谁能不额外加价，谁就更难被替换。做垂直 coding 工具的人需要尽快找到模型厂订阅覆盖不到的场景。

### 6. Thariq：靠 Opus 5.5 一句话把 side project 迁到 Managed Agents

[查看原文](https://x.com/trq212/status/2108689101503566319) · 来源：Thariq (@trq212)

Thariq 说加入 Anthropic 之前，他用 Opus 4 花两周 hack 了一个 side project，基于 Agent SDK，需要常驻进程且跑得不太稳。后来他给 Opus 5.5 一句话，就把它迁移到了 Claude Managed Agents，并且可靠性明显变好。这条的价值在具体机制：把常驻进程、状态和调度交给托管层，能直接吃掉一类最常见的 agent 工程坑。我的判断是，agent 开发的差异化正在从 orchestration 代码转移到任务与工具设计——能托管的部分会被平台吃掉，builder 该把精力放在别人托管不了的业务语义上。

### 7. Nan Yu：从手写代码到 tab-complete prompt

[查看原文](https://x.com/thenanyu/status/2108671762984731037) · 来源：Nan Yu (@thenanyu)

Nan Yu 描述了一条演进路径：先手写代码，再 tab 补全代码，然后变成 prompt agent，现在连 prompt 本身也开始被 tab 补全。这是一个很小但很具体的交互变化——它说明 agent 已经被当成一种可预测、可自动补全的常规输入层，而不是需要郑重对待的对话框。对做 IDE 和 coding tool 的人来说，这意味着 prompt 补全、上下文预填、状态提示会变成基本功能。我的判断是，谁先让 prompt 写起来像写代码一样有补全和类型检查，谁就更接近把 agent 用成生产力而不是玩具。

### 8. Anthropic 工程博客：把大脑和手解耦来扩展 Managed Agents

[查看原文](https://www.anthropic.com/engineering/managed-agents) · 来源：Anthropic Engineering

Anthropic 工程博客讲 Managed Agents 的扩展方式，核心是把决策的大脑和执行的手解耦。这条和 Thariq 的个人迁移经历正好对上：开发者不想自己维护常驻进程和调度，就把它交给托管层，只保留任务语义。对做 agent 平台的团队来说，这种解耦是绕不开的结构问题——执行环境要不要持久、状态放哪、失败如何重试，都会直接决定 agent 能不能跑长任务。我的判断是，未来一年 agent infra 的竞争点不在模型调用，而在这些执行层的脏活谁做得更稳。
