## 今日判断

我今天盯的还是 coding agent 这条线。Thariq 和 Swyx 的几条合起来讨论同一件事：一次会话里 agent 该拿多大自主权，以及怎么确认它真的做完了。点赞高的不是模型能力帖，而是讲任务怎么切、产物怎么验证、失败怎么回滚的帖子，说明一线用 agent 的人已经过了尝鲜阶段，卡点在兜底成本。

企业侧我也看了。Aaron Levie 的价值在于把权限、数据边界、审计这些不好演示的东西摆上台面。同一天 Garry Tan 谈 infra、Matt Turck 谈模型层，放在一起看：模型本身越来越像公共品，被反复讨论的是编排层和成本结构，谁管 token 花在哪、agent 出错之后谁负责。

我的判断是，接下来两个月拉开差距的不是选哪个模型，是你能不能把 agent 的失败路径做成可见的。今天最值钱的信息都来自每天在真实仓库里跑 agent 的人，他们讲的坑比任何 benchmark 都具体。做产品的人今天该做的事：回去看看自己 agent 的中间产物有没有人能读懂。

### 1. Thariq：把 agent 的任务拆到能被单步验证

[查看原文](https://x.com/trq212/status/2115188992861970693) · 来源：Thariq (@trq212)

Thariq 讲的是 coding agent 在真实项目里的工作流切分：把一次性大任务拆成能被单步验证的小块，让 agent 每一步都留下可检查的产物，而不是一口气生成几百行再回头 debug。内容来自日常使用，不是评测榜单。我的判断是，agent 产品的竞争点已经从模型能力转到任务切分和验证回路的设计，谁让中间产物更可读、更可回滚，谁才可能在真实仓库里长期跑下去。这条比同一天的模型参数讨论更值得一线 builder 花时间。

<a id="20261029-02"></a>

### 2. Thariq 的高赞帖：agent 的自主权该给到哪一步

[查看原文](https://x.com/trq212/status/2115135857669881939) · 来源：Thariq (@trq212)

这条讨论 agent 的自主权边界：哪些步骤可以放手让它连着做，哪些必须停下来等人确认。它是当天互动最高的内容之一。我的判断是，自主权不是越多越好，而是看每一步的失败代价和可逆性。可逆、便宜、有明确校验信号的步骤可以连着跑；一旦涉及写生产环境、动数据、发外部请求，就必须插入人工确认点。这个原则比任何 agent 框架的默认配置都重要，产品设计时应该把它做成可配置项，而不是写死在 prompt 里。

<a id="20261029-03"></a>

### 3. Aaron Levie：企业里跑 agent 的瓶颈不在模型

[查看原文](https://x.com/levie/status/2115305369799110905) · 来源：Aaron Levie (@levie)

Levie 聚焦企业部署 agent 时真正卡住的地方：权限怎么划、上下文边界在哪、出了事谁负责。这些在 demo 里看不见，但决定了项目能不能从试点走到全量。我的判断是，to B agent 的护城河不在模型调用，而在能不能把企业已有的权限体系和审计要求接进去。做这行的团队如果还在比谁的 agent 会做更多事，方向就偏了，应该先去解决 agent 出错之后的追溯和回滚，这部分做不好，再强的能力也过不了采购那一关。

<a id="20261029-04"></a>

### 4. Garry Tan：agent 产品形态正在被 infra 层重排

[查看原文](https://x.com/garrytan/status/2115193524152860771) · 来源：Garry Tan (@garrytan)

Garry Tan 把 agent 的产品形态和底层 infra 放在一起谈，核心是编排层、token 成本和运行时环境正在重新决定什么样的 agent 产品能活下来。我的判断是，这类投资人观察要打折听，但有一点值得采信：当 infra 层把编排和成本管理标准化之后，应用层的差异化会往垂直场景和数据积累上收。对一线 builder 的实际含义是，别把精力花在自建编排框架上，除非那本身就是你的产品。先想清楚你的 agent 用了哪些别人拿不到的数据和流程，那个才是留下来的东西。

<a id="20261029-05"></a>

### 5. Swyx：coding agent 的能力有多少来自模型，多少来自 harness

[查看原文](https://x.com/swyx/status/2115089887959359988) · 来源：Swyx (@swyx)

Swyx 讨论的是 coding agent 的效果有多少来自模型本身、多少来自外面的 harness，也就是工具调用、上下文管理、重试策略那一层。这个问题直接影响选型：如果模型换代带来的提升有限，投入就应该放在 harness 上。我的判断是，现在大多数团队高估了换模型的收益，低估了上下文组织和工具返回值设计的收益。同样的模型，工具返回结构清晰还是糊成一团，实际完成率能差出一截。做 coding tool 的人应该把 harness 当成一等公民来迭代，而不是每出一个新模型就重写一遍 prompt。

<a id="20261029-06"></a>

### 6. Swyx 补一条：coding agent 的评测该怎么做

[查看原文](https://x.com/swyx/status/2115135448876269782) · 来源：Swyx (@swyx)

这条是 Swyx 对 coding agent 评测方式的补充：用什么任务集、怎么判断一次改动算成功、pass rate 之外该看什么指标。我的判断是，公开的代码评测大多在测一次性生成，而真实使用是长会话、多轮修改、带上下文的，两者分布差别很大。团队如果只盯着公开榜单挑模型，很容易在真实仓库里翻车。更实用的做法是拿自己仓库里最近几十个真实提交做成私有评测集，哪怕只有二三十条，也比公开榜单更能指导决策。

### 7. Amjad Masad：模型能力提升之后，产品该砍掉什么

[查看原文](https://x.com/amasad/status/2115207856496480261) · 来源：Amjad Masad (@amasad)

Masad 讲的是模型能力上来之后，产品里那些为了绕开模型缺陷而做的补丁该被拿掉。这类判断只有真正在做产品的人会给，因为它涉及删自己写过的代码。我的判断是，大部分 AI 产品现在背着历史包袱：早期为兜住幻觉加的规则层、人工确认步骤、模板化输出，模型换代之后反而限制了能力发挥。定期做一次减法比持续加功能更难也更有价值。建议每个季度回头审一遍产品里的兜底逻辑，逐条问现在还需要吗，删掉之后真实场景跑不跑得通。

### 8. Peter Yang：把 AI 塞进日常工作流的一个具体做法

[查看原文](https://x.com/petergyang/status/2115239304092106772) · 来源：Peter Yang (@petergyang)

Peter Yang 给的是一个把 AI 接进日常工作流的具体做法，不是泛泛的提效建议。我的判断是，这类内容的价值不在方法本身有多新，而在于它示范了一种习惯：先把重复动作找出来，再决定是让模型写还是让 agent 跑。很多人的问题不是不会用模型，是从来没把自己的工作拆成可交给 agent 的步骤。对产品经理来说，值得做一次类似的梳理，把一周里重复三次以上的动作列出来，挑一个做成固定流程跑两周，比订阅十个工具都管用。
