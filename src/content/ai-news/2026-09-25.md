## 今日判断

今天我看下来，最值得记的一件事不是某个模型又刷新了分数，而是 agent 的工程结构开始被拆开了。Guillermo Rauch 那套 brain / hands / files 的拆法，加上 Anthropic 那篇 managed agents 讲 decoupling brain from hands，指向的是同一个判断：agent 不再是一个塞进 Mac Mini 里跑一整天的黑盒，而是一条可以被独立调度、独立恢复、独立扩缩的流水线。谁先把这件事做扎实，谁的 agent 才能从 demo 变成产品。

另一个信号来自 Claude Marketplace。Cursor、CrowdStrike、Accenture、Deloitte 这些名字出现在同一个货架上，说明 agent 的竞争正在从模型能力转到分发和接入。过去你比谁的模型强，现在你要比谁能被别人的 agent 调用。这对做开发者工具的人是好事，前提是你的产品得先成为一个可被 agent 消费的接口，而不是一个人等着点的网页。

我自己今天会重点盯两件事：一是 shell 启动时间这种看似琐碎的优化，因为 Rauch 已经在用 agent 做这类细活，说明底层工程才是 agent 真正落地的地方；二是那些敢把 prompt、失败、重启策略摊开讲的人。二手评论越来越不值钱，一手实践的细节才是接下来半年最稀缺的东西。

### 1. Guillermo Rauch：成功 agent 的三个部件，以及云端怎么把它们拆开

[查看原文](https://x.com/rauchg/status/2102820148629614685) · 来源：Guillermo Rauch (@rauchg)

Rauch 把成功 agent 拆成三个部件：brain（模型加 harness 逻辑）、hands（工具、电脑、浏览器）、files（记忆、技能、仓库）。他指出现阶段的懒办法是把三者全塞进一台常开的 Mac Mini，跑 claude 或 fx，靠 caffeinate 撑着。但如果要在云端低成本跑 agent，就必须拆开：harness 放 Fluid compute，用 Workflow 保证事件日志在重启、崩溃、发布之间不丢；hands 交给 Browserbase、Kernel、Sandbox 或 just-bash 这类专用轻量工具；files 的解耦是之前缺的一环。这个拆法的价值在于它把 agent 从一台机器上的黑盒，变成了可以被独立调度和恢复的流水线。我的判断是，未来半年 agent 的竞争不在模型，而在这层结构的成熟度。

### 2. Claude Marketplace 上线：Cursor、CrowdStrike、Accenture 都上了货架

[查看原文](https://x.com/claudeai/status/2102840851538080172) · 来源：Claude (@claudeai)

Claude 上线了 Marketplace，用户可以在这里发现工具、agent 和服务伙伴，接入 Slack、Notion 这类连接器，也可以直接购买 Cursor、CrowdStrike 等公司的 agent 产品，并通过 Accenture、Deloitte 这类服务商做规模化落地。这件事的意义不在货架本身，而在于 agent 的分发逻辑正在形成：过去是用户找工具，现在是 agent 调 agent。对做开发者工具的人来说，这既是机会也是压力，你得先成为一个能被 agent 消费的接口，而不是一个等人来点的网页。我的判断是，接入生态的优先级会第一次超过自建流量。

### 3. Anthropic：把托管 agent 的 brain 和 hands 解耦

[查看原文](https://www.anthropic.com/engineering/managed-agents) · 来源：Anthropic Engineering

Anthropic 工程博客讲的是怎么 scale managed agents，核心动作是把 brain 和 hands 解耦。这和 Rauch 在 X 上那套 brain / hands / files 的拆法几乎是同一个判断，只是从模型侧工程团队的角度给出。这件事的重要性在于，agent 的可靠性问题正在被当成基础设施问题来解，而不是靠模型再聪明一点。解耦之后，harness、工具执行、状态存储可以各自独立扩缩和恢复，崩溃和重启不再意味着整个任务重来。我的判断是，接下来真正拉开差距的不是谁接了更多工具，而是谁的 agent 在长时间运行下还能保持状态一致。

### 4. Rauch：用 agent 优化 shell 启动时间，这件事比看起来重要

[查看原文](https://x.com/rauchg/status/2102947745132924993) · 来源：Guillermo Rauch (@rauchg)

Rauch 说他很在意新 shell session 的启动时间，于是让 agent 去优化 .zshrc 这类配置文件，结果 Opus 5.5 找到了其他模型漏掉的一堆优化点，他甚至为此做了个 ShellPerfBench。这条看起来像程序员洁癖，但信息量在于：agent 已经开始做那种没人愿意手动去抠的底层性能活，而且发现了人类和别的模型都漏掉的东西。我的判断是，这类琐碎但可复现的优化，才是 agent 从演示走进日常工程的地方。你可以不喜欢 Rauch 对启动时间的执念，但你得承认，愿意让 agent 碰 .zshrc 的人，和只让它写 demo 的人，产出会越差越远。

### 5. Thariq：一句 Claude one-shot this，背后是一万字的 prompt

[查看原文](https://x.com/trq212/status/2102870353781641416) · 来源：Thariq (@trq212)

Thariq 把那种 Claude 一次就搞定了的帖子拆开看，背后其实是一万字左右的 prompt，包含好的判断、skills、例子和 API keys。这条的价值不是说模型不行，而是说 one-shot 这个叙事本身在误导人。真实工作流里，输出质量的大头来自你喂进去的上下文和约束，而不是模型凭空发挥。我的判断是，接下来六个月，把 prompt、skills、示例组织好的人，会比只换更强模型的人拉开更大差距。对做 coding tool 和 agent 的人来说，这句话的意思是：别只优化模型调用，去优化你给它的那套上下文结构。

### 6. Thariq：一种新的工作流分享形式，直接给可复现的 prompt 和技巧

[查看原文](https://x.com/trq212/status/2102857025206255902) · 来源：Thariq (@trq212)

Thariq 说这是他们在尝试的一种新内容形式：不展示结果，而是深入讲他们怎么用具体的 prompt 和技巧完成工作，并且这些内容应该是你能照着复现的。他同时问读者这样是否有用。这条的重要性在于，它把 AI 内容的单位从我做出了什么，换成了你怎么自己做出什么。对一线 builder 来说，这种格式比任何评测榜都更有用，因为它是可以照抄的工作流。我的判断是，接下来会有更多人被迫从晒结果转向晒方法，谁先把方法摊开，谁就更容易建立可信度。

### 7. Swyx：AINews 默认模型换成 Opus 5.5，理由是少废话

[查看原文](https://x.com/swyx/status/2102650014552182920) · 来源：Swyx (@swyx)

Swyx 说他拿 Latent Space 的 AINews 和 6 Sol 并排跑过，差距很明显，Opus 5.5 的报告更简洁、更有品味，废话比 5 Opus 还少。所以他把 AINews 的默认模型换成了 Opus 5.5。这条值得记的原因是，模型选型在这里不是看榜单，而是看它在真实内容工作流里能不能少产出 slop。对一个每天要处理大量信息的人来说，少废话本身就是生产力。我的判断是，模型在写作和摘要类工作流里的差距，正在从谁更聪明，转向谁更克制。

### 8. Boris Cherny：Claude 在用类似形式化验证的方式找 bug

[查看原文](https://x.com/bcherny/status/2102898067133595992) · 来源：Boris Cherny (@bcherny)

Boris Cherny 给形式化方法背景的人解释 Claude 现在在做什么：先对程序建模，重点针对容易出状态机和竞态问题的部分；在模型里找反例，这些反例就是疑似 bug；然后复现 bug，再在代码里修掉。他强调并不是整个代码库都被形式化验证，而是最棘手的那部分被建模、检查反例并修复。这条的价值在于它给出了一种具体的 agent 修 bug 机制，而不是笼统地说 AI 会写代码。我的判断是，coding agent 的下一步竞争点在于能不能锁定代码里最容易出事的那一小块，而不是覆盖全仓库。
