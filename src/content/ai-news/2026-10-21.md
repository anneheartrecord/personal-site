## 今日判断

今天我看下来，最值得记的是 Aaron Levie 那段关于应用层的问题：模型越强，企业落地越难把智能分发到具体业务里。他的判断是差异化反而上升——当模型只能吐 token 时你只能做 wrapper，但当 agent 能跑几小时甚至几天的任务、需要协调多个 agent、需要 domain-specific 的数据源和路由时，真正的工程都在领域里。这跟我自己的体感一致：现在做企业 agent，难点不在调模型，在把任务拆到可执行、可观测、可回滚。

第二个信号是 agent 的持久化正在变成基础设施问题。Guillermo 把 v0 的 HTML artifact builder 开源，明说是为了让 agent durable——扛住 server crash、LLM 抖动、function 限制。这不是炫技，是把 agent 从 demo 变成能一直跑的东西。Wabi 2.0 那种 orchestrator 加 episodic chats 的结构也是同一件事的另一面：不是让一个 agent 什么都干，而是让多个短命对话围绕一个主脑组织，还能分享给同事。

我的判断是：接下来半年 builder 的胜负手不在 prompt，在状态管理和任务编排。谁能让 agent 崩溃后接着跑、让长任务有 checkpoint、让多个 agent 有明确的目标协调，谁就能进真实工作流。纯对话式产品会继续被消耗，但不会消失，它会退到一个更小的位置。

### 1. Levie：模型越强，企业应用层的差异化反而越大

[查看原文](https://x.com/levie/status/2112404676436222170) · 来源：Aaron Levie (@levie)

Levie 提出应用 AI 层的核心问题：模型变强后，怎样把智能分发进企业。他的反直觉判断是，模型能力越强、越能跑长任务和用工具，按领域做差异化的空间反而更大。模型弱的时候你只能做 wrapper，用 prompt 加有限 RAG 吐 token；但到了 agent 时代，任务跑几小时甚至几天、工作流触发 agent、多个 agent 围绕目标协调、需要 domain-specific 数据源和路由、需要真正的变革管理，这些都不是模型本身能替代的。我的判断是，这条对正在做企业 agent 的 builder 很关键：护城河从模型能力转向领域编排和落地深度。

<a id="20261021-02"></a>

### 2. Vercel 开源极快 HTML artifact builder，重点在让 agent 可持久运行

[查看原文](https://x.com/rauchg/status/2112247046082363821) · 来源：Guillermo Rauch (@rauchg)

Guillermo Rauch 宣布开源一个非常快的 HTML artifact builder，底层用 libfx，核心卖点是让 agent 变得 durable。他直言，为 v0 搭建低层管道以扛住服务器崩溃、LLM 抖动、function 调用限制，过去是巨大痛点，现在这套东西免费开源。这不是又一个 UI 组件，而是把 agent 从 demo 推进到能持续运行的工程基础设施。我的判断是，agent 的可靠性问题正在被拆成可复用的底层件，谁能先解决崩溃恢复和状态延续，谁的产品就能进真实工作流。

### 3. Wabi 2.0 把个人 agent 拆成 orchestrator 加 episodic chats

[查看原文](https://x.com/nikunj/status/2112219327881761008) · 来源：Nikunj Kothari (@nikunj)

Nikunj 复盘 Wabi 2.0：1.0 设计好看但没留住他，2.0 一上手就抓住他，因为它把个人 agent 的结构做对了。他把当下个人 agent 分两类：单聊式（iMessage、Muse）难以在多头事务里切分；自建多 agent（Hermes）能共享上下文但永久存活、缺乏边界。Wabi 用主 agent 做 orchestrator，加上按主题划分、单一目的的 episodic chats，还能把某个 chat 分享给家人。我的判断是，这是把 agent 从单一对话窗口转向有层级、可分享的工作单元，对做个人生产力 agent 的团队有直接参考。

### 4. Every 团队用持久 agent 两周后的真实用例复盘

[查看原文](https://www.youtube.com/playlist?list=PLuMcoKK9mKgHtW_o9h5sGO2vXrffKHwJL) · 来源：AI & I by Every

Every 团队在 OpenAI 持久 agent 上线两周后做了一次内部复盘：团队约 30 人开始采用，作者本人早在此前就把它当主要交互方式。文中列出的用例很具体——有人用它扫孩子学校邮件并提炼要点，运营负责人发现它会捕捉公司内跨 Slack 的账号申请并询问是否直接批准。这些不是演示场景，是真实工作流里 agent 主动介入的痕迹。我的判断是，持久、主动的 agent 价值不在单次回答质量，而在它替人盯着那些容易被漏掉的琐事。这正是企业 agent 落地该被评估的维度。

### 5. Thariq：和 agent 多任务并行的人，多数应该慢下来

[查看原文](https://x.com/trq212/status/2112219173288120531) · 来源：Thariq (@trq212)

Thariq 提出，多数用 agent 多任务并行的人应该慢下来：你同时在推的大部分事情其实没那么重要，先问自己 P0 是什么，如果给这件事全部注意力会是什么样。这条不是工具评测，而是对 agent 使用方式的反思。我的判断是，工具越能并行，人的注意力分配就越成为瓶颈；把 agent 当成同时开十个任务的手段，最后往往是十个半成品。对做 agent 产品的团队来说，这也是个提醒：默认多任务不一定是对的交互，帮用户收敛优先级可能比帮用户开更多任务更有价值。

### 6. Garry Tan：多人协作 agent 就是群聊，Wabi 已经做出来了

[查看原文](https://x.com/garrytan/status/2112278352514162834) · 来源：Garry Tan (@garrytan)

Garry Tan 简短判断：多人协作 agent 以群聊形态出现几乎是必然的，而 Wabi 已经把它做出来了。这和 Nikunj 对 Wabi 2.0 的结构分析形成互补——一边是从产品结构拆解 orchestrator 加 episodic chats，一边是从形态判断群聊会成为多人 agent 的默认界面。我的判断是，个人 agent 和团队 agent 的分野正在变清晰：个人 agent 解决注意力分配，团队 agent 解决共享上下文和权限。做这一层产品的 builder 需要想清楚自己的默认协作单位是谁。
